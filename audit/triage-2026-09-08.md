## Réels et confirmés

### R1 — `stage_files()` casse sur un fichier mise en sous-répertoire (spark #2, glm #1)

`src/sandbox/mise.rs:217-231`. **Confirmé par exécution** (sonde temporaire dans le `mod tests`,
retirée depuis) : `stage_files` avec le nom `.config/mise/config.toml` rend
`No such file or directory (NotFound)`.

Chaîne complète, sans filtre intermédiaire :
`MISE_CONFIG_NAMES` (`src/trust.rs:62-72`, **4 des 9 noms portent un slash** :
`mise/config.toml`, `.mise/config.toml`, `.config/mise.toml`, `.config/mise/config.toml`)
→ `mise_files_for` → `mise_inputs_for` (nom **relatif au projet**, slash conservé, `trust.rs:104-112`)
→ `MiseConfig.files` (`config/load.rs:685`) → `mise_env` (`launch/build.rs:3102`) → `stage_files`.

Condition d'atteinte : projet **trusted** portant l'une de ces 4 formes. Effet : `map_err` →
`sbx: mise [env] resolution failed: No such file or directory` → `ExitCode::FAILURE`, **lancement
avorté**. Le doc-comment de `mise_env` le confirme : « A trusted `[env]` that cannot be resolved is
fatal ».

`git log -S` ne montre aucun remède antérieur, et **aucun test ne couvre ces 4 noms** : le test
unitaire (`mise.rs:697`) n'exerce que `.mise.toml`, et les seuls hits de `tests/` (`app.rs:56,536`)
portent sur le home d'une app (`sbx/apps/<app>/home/.config/mise`, le registre de `mise use`), pas
sur un fichier mise du projet découvert par `mise_files_for`.

Détails aggravants exacts : le tmp `format!("{name}.{pid}.tmp")` contient lui aussi le slash ;
`create(true).truncate(true)` sans `create_new`/`O_NOFOLLOW`.

### R2 — un broker `tcp://[::1]:port` ne marche jamais — mais pas par le mécanisme décrit

Le **fait** est réel ; **les deux rapports nomment le mauvais site et le mauvais mécanisme.**

Mesuré (sonde sur `l4_decision`, retirée depuis) :

    l4_decision("[::1]", 5432) -> NoMatch
    l4_decision("::1",   5432) -> Splice(Rule { kind: Ip(::1, ...) })
    canonical_host("[::1]") = "[::1]"   canonical_host("::1") = "::1"

Ce qui se passe réellement : `parse_tcp_endpoint` (`config/mod.rs:3572`) garde `[::1]` verbatim ;
l'admission `launch/build.rs:1389` demande `l4_decision(host, port)` → **NoMatch** → le broker
**n'est pas démarré**, avec le message « add `tcp://[::1]:5432` to `[network] allow` » — c'est-à-dire
exactement ce que l'utilisateur a déjà écrit. Le `connect` de `broker.rs:1361` **n'est jamais atteint**.

Donc : fail-closed avec un message trompeur, et non « endpoint mort-né qui échoue en EAI_NONAME ».
(Le `connect` bracketté échouerait bien — vérifié séparément, `EAI_NONAME` — mais il est hors d'atteinte.)

Second point : la « preuve » citée par les deux rapports (`completion.rs:2021`, `tcp://[::1]:22`)
concerne **un autre parseur**, `parse_tcp_target` (`allowlist/grammar.rs:538`), qui **dé-brackette
correctement**. C'est le parseur des règles d'egress, pas celui du broker. Aucun exemple de la doc
broker (`docs-site/docs/guide/configuration/broker.md:41`) n'utilise la forme brackettée.

Sévérité réelle : basse-moyenne. Le remède reste bon (dé-bracketter dans `parse_tcp_endpoint`),
mais il faut le tester **à l'admission**, pas au connect.

### R3 — la couche globale tombe sur une erreur non-NotFound : fait vrai, conséquence fausse

`config/load.rs:706-728` (`read_layer`) + `:443` (`read_global`). Le fait est exact : tout `Err`
autre que `NotFound` → warning + couche entière droppée.

**La conséquence annoncée par les deux rapports est fausse.** Mesuré :

    NetworkPolicy::default() = Allowlist
      default_action = Deny
      allow rules    = 0
      deny rules     = 0

Perdre la couche globale ne peut donc **pas** ouvrir l'egress : le défaut est deny-by-default avec
zéro règle d'autorisation, soit plus fermé que toute allowlist écrite. « launch en egress ouvert »
(spark #4) et « the launch proceeds with the default posture » (glm #3) ne suivent pas.

**Le constat tient néanmoins, par une autre table.** `ProcMode::default()` est `Off`
(`src/proc_policy.rs:46-50`), et `[proc]` est bien accepté depuis la couche globale — confirmé dans
le code, pas seulement dans la doc : `config/mod.rs:565` (« the default (`off`) unless the global
config or a trusted [project] ») et `:1968-1981` (« trusted by location at the global layer »,
`proc_origin = Provenance::Global`). Donc : un `[proc] mode = "enforce"` écrit dans la config **globale** et perdu
par cette voie **désactive le lens de processus**, avec un simple avertissement. Toute table dont le
défaut est plus permissif que ce que l'utilisateur y écrit est concernée.

Atteignabilité : plus large que l'`EMFILE`/`ENOSPC` cité, car le garde-fou de sécurité déclenche
lui-même le fail-open. `read_safe_bytes` (`config/safety.rs:85`) passe par `check_safe_file` →
`verdict` (`:22-37`), qui refuse en `PermissionDenied` — donc pas `NotFound` — un fichier
**non régulier**, un fichier **dont le propriétaire n'est pas l'euid**, un fichier
**world-writable**, plus le dépassement de `MAX_CONFIG_BYTES` (1 MiB).

Le cas réaliste est le deuxième : un `~/.config/sbx/sbx.toml` restauré ou copié sous `sudo`
appartient à `root`, donc l'euid ne correspond plus, donc **toute la couche globale tombe** avec un
avertissement. (Le group-writable est explicitement toléré — `safety.rs:152-153` — et un lien
symbolique passe, puisque l'ouverture suit le lien et le `fstat` porte sur la cible : stow/chezmoi
ne sont pas touchés.)

C'est une décision de posture, pas un bug binaire : à arbitrer.

### R6 — `loop_for()` avale trois classes d'erreur, contre son propre contrat (spark §4)

`src/storage.rs:429-448`. Le doc-comment de la fonction énonce l'enjeu : « A missed match is not a
missed optimization here: **it is the second attachment this function exists to prevent**. » Or trois
chemins d'erreur y rendent silencieusement « aucun loop attaché » :

    let Ok(entries) = std::fs::read_dir(sys_block) else { return Ok(None) };   // :430
    for e in entries.flatten() {                                              // :434
        let Ok(target) = std::fs::read_to_string(&backing) else { continue };  // :440

`state()` (`:469`) traduit ce `None` en `State::Detached`, c'est-à-dire l'invitation à attacher une
seconde fois — la corruption que le module documente lui-même (`storage.rs:416-420`). Aucun verrou
n'entoure `loop-setup` (aucune occurrence de `lock` dans `storage.rs`), donc rien ne rattrape en aval.

Ce qui rend le constat solide est une **asymétrie interne**, à la ligne suivante : la lecture de
`/proc/self/mountinfo` (`:476`) est propagée par `?` avec précisément ce raisonnement — « Propagated,
not defaulted. […] A table that cannot be read is not a volume that is unmounted. » Le même principe
est appliqué à `mountinfo` et pas aux trois lectures de `loop_for`.

Nuance sur le 3e chemin : `/sys/block/loopN/loop/` n'existe que pour un loop **lié**, donc un
`NotFound` y est l'état normal d'un loop libre et le `continue` est correct. Sur cette machine, les
24 loops présents sont tous liés (snapd) — le cas libre n'a pas pu être mesuré ici. Le trou n'est
donc pas « trois classes d'erreur » mais **tout `Err` autre que `NotFound`** sur les chemins 2 et 3,
plus l'échec de `read_dir` au chemin 1 : exactement la distinction que `read_layer` fait déjà (R3),
et c'est la forme que doit prendre le remède.

Atteignabilité mince. **Correction de ma propre sévérité, mesurée au second lot** : `up()` prend
`lock_image` (`storage.rs:1219`), « what keeps two loop devices off one image », donc le scénario
« deux `up()` concurrents » que j'avais invoqué est déjà fermé. Ce que le verrou ne couvre pas, et
qui reste le fond du constat : un attachement **préexistant** (posé hors sbx, ou par une session qui
a depuis relâché le verrou) que `loop_for` ne détecte pas, après quoi `up()` pose un second loop sur
la même image. L'asymétrie interne avec `mountinfo` est le cœur du constat et ne dépend pas de
cette nuance.

### F7 — « `sbx search foo bar` ignore `bar` en silence » (spark, CLI) — *et mon propre R4*

**Faux, et l'erreur est la mienne** : j'avais d'abord retenu ce constat. Le comportement est

deliberate one: nixhub matches a single token, so a multi-word search has nothing to carry — quote
a phrase to pass it as one argument. » Un test l'affirme (`search.rs:97`). Et surtout, la doc
utilisateur le publie : `docs-site/docs/guide/cli/search.md:13` — « Only the first word is searched;

J'avais lu le corps de la fonction à partir de la ligne 20, sous le doc-comment, et cité comme

contrat, et il ne redevient un défaut que si la doc utilisateur promet le contraire. Ici elle promet
l'inverse.

## Faux positifs (mesurés)

### F1 — « symlinks jamais détectés » dans `storage.rs` (spark #1, sa **priorité 1 critique**)

**Faux, prouvé par exécution.** `DirEntry::metadata()` ne suit **pas** les liens (contrairement à
`fs::metadata(path)`) :

    dir_link   entry.metadata: symlink=true dir=false file=false
    rel_link   entry.metadata: symlink=true dir=false file=false
    abs_link   entry.metadata: symlink=true dir=false file=false
    real.txt   entry.metadata: symlink=false dir=false file=true

`census()` (`storage.rs:801`) et `copy_tree()` (`:854`) sont corrects ; `copy_tree` recrée les liens
via `read_link` + `symlink` (`:857-859`). Tout ce qui en découlait tombe : pas de double taille, pas
de dedup `.links` perdue, **pas d'exfiltration de `/etc/shadow`**. glm avait raison de le rejeter.

### F2 — `proc pending allow/deny` sans `Page`

Faux. La `Page ["proc","pending"]` (`help/pages.rs:528-550` à HEAD) documente la forme dans son
**synopsis** (`sbx proc pending [allow|deny <id>]`), dans **trois entrées d'options** et dans sa
prose. `allow`/`deny` y sont des **arguments**, pas des commandes. Les gardes du projet le
confirment : `cargo test --bins help::` et `docs_coverage` passent (16/16 chacune).

### F3 — `--source manual` « indiscoverable, erreur mensongère »

Faux. `cli/net/rules.rs:54-55` porte le commentaire : « `session` is the live `--session`-answered
overlay; `manual` is kept as an accepted alias for the same source. » C'est un alias de
compatibilité délibéré ; la complétion et le message d'erreur listent le nom canonique. Ne pas
annoncer un alias hérité est le comportement correct.

### F4 — `sops://../../` sort du projet (spark §5)

Faux comme défaut. `sops_path` (`sandbox/egress.rs:1477`) accepte **délibérément** les chemins
absolus (`if file.is_absolute() { file.to_path_buf() }`) : normaliser les relatifs n'ôterait donc
aucun pouvoir. Et `[secret]` est un champ de sécurité, dans le code et non seulement dans la doc :
`config/mod.rs:2592` (« The `[secret]` section is a security field — a trusted project may inject »)
et `:2111` (« Secrets are trusted by location at the global layer »), ce que
`docs-site/docs/guide/configuration/secret.md:13` publie. L'auteur du chemin est donc déjà celui à
qui l'utilisateur a accordé sa confiance.

### F5 — `scan_max_kb` : fait vrai, sévérité fausse

Le raw est `Option<i64>` (`config/schema.rs:701`), la garde est `Some(kb) if kb > 0`
(`config/manage.rs:907` à HEAD) : `i64::MAX` passe, `saturating_mul(1024)` sature, et
`usize::try_from` réussit sur 64 bits. Mais l'effet est un plafond de lecture **plus grand**, donc un
scan **plus complet** — un coût, pas un contournement. Vérifié en aval : `OpenPolicy::compile`
(`open_policy.rs:117-142`) ne refuse aucun plafond absurde (`max_scan: max_scan.max(1)`), donc rien
ne rattrape la valeur plus loin — le fait tient entièrement, c'est la **sévérité** qui est fausse.
Classé « Majeur » par spark : à tort.

### F6 — « `pin_sources` ne pinne rien » quand `canonicalize` échoue (spark §5)

Faux. `launch/build.rs:98` retombe sur `project.to_path_buf()`, et le doc-comment juste au-dessus
répond mot pour mot au constat : « A path that cannot be canonicalized […] is carried through as
written rather than dropped — **pinning on the literal path is worth more than pinning on nothing**. »
Le pire cas est un pin sur un chemin non résolu, pas une cage RW non pinnée. Nouvelle occurrence du
biais dominant : le commentaire par lequel le code expose sa limite est cité comme preuve du défaut.

- **N6 — boucle `accept` détachée.** Documenté : « The accept loop is detached and **dies with
  sbx**; this guard owns the socket file and unlinks it. » Le `Drop` fait ce qu'il annonce.
- **N7 — `poll(-1)` du WebSocket** — faux comme fuite, mais le contrat est plus étroit que sa
  phrase. « Indefinite: an idle live channel parks here, not in a read, so it is never cut » est la
  sémantique voulue d'un tunnel, et un pair qui ferme proprement envoie un FIN qui réveille le
  `poll`. Mesuré en revanche : **aucun `SO_KEEPALIVE` sur tout `src/sandbox/proxy/`, et aucun
  `shutdown()` dans `websocket.rs`** (les hits « keepalive » sont des fixtures de bench). Un pair
  qui disparaît *sans* FIN — cage tuée dur, perte réseau — laisse donc le thread parqué jusqu'à la
  fin du processus. Le commentaire couvre l'idle vivant, pas le mort silencieux : la borne est la
  vie du superviseur, pas celle du pair.
- **N8 — `splice.rs set_timeout(None)`.** Le symbole n'existe pas et n'a jamais existé
  (`git log -S` vide) : site inventé.
- **N9 — join des lecteurs après `kill`.** bwrap est l'init du namespace pid : « nothing outlives
  the ceiling », donc les tubes ferment et le join retourne.
- **N10 — `host_exec_verdict`.** Le group-writable est toléré **comme pour les fichiers de config**
  (cohérent avec `safety.rs::verdict` — pas d'asymétrie), et le `stat`-puis-`execve` est nommé :
  « against a same-uid attacker — who already owns the account and could replace sbx itself —
  nothing at this layer is a boundary ». `security-model.md` publie cette position.
- **N16 — garde symlink de `bounded_unpack`.** Mesuré sur GNU tar 1.35 : l'écriture à travers un
  lien membre est **refusée** (« open impossible »), la victime intacte. Le script propage l'échec
  (`if ! … then exit 1`), et l'absence de limite sur le *nombre* de membres est publiée dans
  `packages.md` — la limite écrite était déjà le remède retenu.
- **N17b — les autres écarts CLI.** `gc --optimize` est un alias de `--optimise`, qui est au
  synopsis ; `upgrade --app`/`--project` sont bien dans leur page ; `bundle export` a sa `Page` et
  son dispatch ; `session logs` documente les formes courtes qu'il accepte.
