## [1.9.0] - 2026-04-29

### Fixed
- **`OPS_BUILD_ARGS[default]` now actually applies to unkeyed builds.** Pre-fix, the lookup gated on `_OPS_IMAGE_KEY` being non-empty (set only when `-i <key>` matched an `OPS_IMAGES` entry), so `OPS_BUILD_ARGS[default]` declared on its own — without a matching `OPS_IMAGES[default]` — was silently ignored. The user did `ops config set 'OPS_BUILD_ARGS[default]' 'EXTRA_MISE_TOOLS=nix:terraform'`, ran `ops update`, and the resulting image had `EXTRA_MISE_TOOLS=` empty in its build args (`docker history` confirmed) — terraform absent without any visible error. Post-fix, the lookup key falls through to `default` when no profile matched (`local _build_args_key="${_OPS_IMAGE_KEY:-default}"`), so `OPS_BUILD_ARGS[default]` is honored on `ops build` (no `-i`) without requiring an `OPS_IMAGES[default]` declaration. The natural reading of the array key name now matches the runtime behavior. The same fix applies to `current_hash()` so cache invalidation is correct when only `OPS_BUILD_ARGS[default]` changes. Per-profile entries (`OPS_BUILD_ARGS[arch]` etc.) still require their matching `OPS_IMAGES[<key>]` — falling back to `default` for unkeyed lookups doesn't change that contract.

  Coverage: 4 new tests in `tests/test_build_flags.bats` — `OPS_BUILD_ARGS[default]: applies to unkeyed build (no -i flag)`, `OPS_BUILD_ARGS[default]: works without an OPS_IMAGES[default] entry (no pairing required)` (regression test for the silent-ignore footgun), `OPS_BUILD_ARGS[default]: explicit -i <key> overrides the default fallback` (asserts the per-profile entry wins exclusively, no merge with `[default]`), and `OPS_BUILD_ARGS[default]: applies as fallback when -i points to a raw image ref` (locks the post-fix behavior on the raw-ref path — pre-fix the raw-ref path skipped `OPS_BUILD_ARGS` entirely; post-fix the lookup falls through to `default` when no profile key matched). Plus 2 cache-invalidation tests in `tests/test_hash.bats` — `warning when OPS_BUILD_ARGS[default] is added after build` and `warning when OPS_BUILD_ARGS[default] is mutated after build` — which guard the `current_hash()` mirror of the build-time fix (without that mirror, the per-image hash cache would go stale silently when the user adds or edits `OPS_BUILD_ARGS[default]`). Existing `OPS_BUILD_ARGS: ignored when -i points to a raw image ref (no key)` still passes — the test config has no `[default]` entry, so the fallback is empty and no args propagate.

### Removed
- **`google-chrome` is no longer in the image baseline.** The 1.8.0 release moved chrome from "default value of `EXTRA_MISE_TOOLS`" into the hard-coded baseline `mise use -g` line, on the rationale that "every user of chrome-devtools-mcp gets it out of the box". In practice the cost (~300 MB image bloat, the unfree-license question forced on every user, no opt-out for users who don't need a browser) outweighed the convenience. After this release the Dockerfile baseline is `nix:git github:cli/cli github:BurntSushi/ripgrep github:jqlang/jq github:ast-grep/ast-grep node@lts` — chrome is opt-in via `EXTRA_MISE_TOOLS` like every other browser-like dependency. The wrapper, env vars (`CHROME_PATH`, `PUPPETEER_EXECUTABLE_PATH`), and the three discoverability symlinks (`/usr/bin/google-chrome`, `/opt/google/chrome/chrome`, the PATH-prefixed `/opt/ops/bin/google-chrome`) all still ship in the image — they short-circuit with a discoverability message when chrome is absent and converge on the wrapper when it's present, so the opt-in story is "set it once, everything works the same as before".

  Migration recipe (the simple form — bake chrome into the default image):

  ```bash
  ops config set 'OPS_BUILD_ARGS[default]' 'EXTRA_MISE_TOOLS=nix:google-chrome'
  ops update default
  ```

  The `OPS_BUILD_ARGS[default]` fallback is supplied by the unkeyed-build fix in the same release (see the "Fixed" entry above) — pre-fix, this single-line recipe would have silently no-op'd. Per-profile pattern (chrome side-by-side with a lean default) is still available — see README "Build-time tools" → "Adding google-chrome (or another browser)" for both recipes.

### Changed
- **`scripts/google-chrome.sh` wrapper error message updated** to reflect the chrome-not-in-baseline contract. The message now points at the `OPS_IMAGES + OPS_BUILD_ARGS` opt-in recipe instead of the obsolete "rebuild the image to repopulate the baseline" advice.
- **`tests/test_image_integration.bats`** updated for the new contract: the obsolete "google-chrome --version starts Chrome successfully" test (was asserting chrome runs out-of-the-box, no longer true post-baseline-removal) was **deleted** rather than flipped to assert chrome's absence — an absence-check would be a brittle false-negative the moment a user opt-ins chrome via `OPS_BUILD_ARGS[default]='EXTRA_MISE_TOOLS=nix:google-chrome'`, and the existing `image: chrome wrapper emits help message when binary is missing` already covers the wrapper's not-installed path robustly (it temporarily moves the chrome binary aside, so it works regardless of whether chrome is opt-in or not). The baseline-config assertion (`@test "image: baseline config in /etc/mise/config.toml contains expected tools"`) was relaxed to assert only the presence of core baseline tools (`nix:git`, `node`); the prior `[[ "$output" != *"nix:google-chrome"* ]]` / `[[ "$output" != *"nix:semgrep"* ]]` absence assertions were dropped for the same reason. The wrapper-error-message assertion updated to match the new "google-chrome is not part of the image baseline" string.
- **README** rewrote the "Build-time tools" section to: drop the "baseline ships chrome" claim, document the `OPS_IMAGES + OPS_BUILD_ARGS` pairing requirement (with a ⚠ block and a `docker history` debugging hint), and add an "Adding google-chrome (or another browser)" sub-section showing the per-profile recipe (`-i chrome` for chrome workloads, lean default for everything else) plus the `[default]` override variant for users who want chrome baked into their default image. The TL;DR (line 5) and the GUI/Wayland section dropped their "in the image baseline" chrome references.
- **`docs/dockerfile-design.md`** §"Why `/etc/mise/config.toml` for the baseline" updated to list the actual current baseline tools (no chrome).

## [1.8.0] - 2026-04-28

### Removed
- **`semgrep` is no longer in the image baseline.** Pre-1.8.0 the Dockerfile baked `nix:semgrep` into the system-wide `mise use -g …` line at build time, so every `ops run` had `semgrep` on PATH whether the user wanted it or not. Post-1.8.0 it's gone from the baseline and not in the default `EXTRA_MISE_TOOLS` either — users who want it back add it via `OPS_BUILD_ARGS`. Rationale: the baseline should ship the strict minimum that every container needs (git, browser for chrome-devtools-mcp, AI-agent runtime); domain tooling belongs in user-controlled `EXTRA_MISE_TOOLS` so the image stays small for users who don't run that tool category. Migration: `ops config set 'OPS_BUILD_ARGS[<image-key>]' 'EXTRA_MISE_TOOLS=nix:semgrep'` then `ops -i <image-key> build` to restore.

### Changed
- **`google-chrome` moved into the image baseline.** It used to live in the *default value* of `EXTRA_MISE_TOOLS` (`ARG EXTRA_MISE_TOOLS="nix:google-chrome"`), which had a footgun: any `OPS_BUILD_ARGS[<key>]="EXTRA_MISE_TOOLS=…"` override silently dropped chrome unless the user remembered to re-list it. After 1.8.0 chrome is hardcoded in the baseline `mise use -g` block (next to `nix:git`, `github:cli/cli`, etc.), so it's always present and `EXTRA_MISE_TOOLS` overrides become **purely additive** — list what you want on top of the baseline, no risk of dropping something you didn't intend to. The behavioural promise "chrome works out of the box for `chrome-devtools-mcp`" stays identical; only the implementation shape changed.
- **`ARG EXTRA_MISE_TOOLS=""` is now the default** (was `"nix:google-chrome"`). Combined with the chrome → baseline move above, the new contract is: baseline = always there, untouchable from `OPS_BUILD_ARGS`; `EXTRA_MISE_TOOLS` = pure addition layer, empty by default. Means `ops config set 'OPS_BUILD_ARGS[<key>]' 'EXTRA_MISE_TOOLS=nix:terraform'` adds terraform without losing anything else, where pre-1.8.0 you had to remember `'EXTRA_MISE_TOOLS=nix:google-chrome nix:terraform'`.
- **`scripts/google-chrome.sh` wrapper error message updated.** When the Chrome binary is missing (e.g. `ops-share-mise` volume reset before mise had time to repopulate it), the wrapper used to say "rebuild with `--build-arg EXTRA_MISE_TOOLS=nix:google-chrome`" — accurate pre-1.8.0, but obsolete now that chrome is in the baseline. The new message tells the user to rebuild the image, and points at `OPS_BUILD_ARGS` for users who want a different browser instead (e.g. `EXTRA_MISE_TOOLS=nix:chromium`).

  Coverage: `tests/test_image_integration.bats:86` (baseline assertion) flipped from `[[ "$output" == *"nix:semgrep"* ]]` to `[[ "$output" != *"nix:semgrep"* ]]` (semgrep absent; chrome still asserted present); `tests/test_image_integration.bats:416` updated to match the new wrapper error string (`image baseline ships google-chrome`). README's "Build-time tools" section (`README.md:423`+) was rewritten end-to-end to describe the new baseline / additive-EXTRA_MISE_TOOLS contract; line 5 (TL;DR), line 1190 (GUI/Wayland section's chrome reference), and `docs/dockerfile-design.md:208` + `:222` were updated for the same reason.

## [1.7.0] - 2026-04-28

### Fixed
- **`ops info` no longer mis-renders dangling images labelled `ops.dockerfile`.** When a build leaves the previous image untagged (typical after `ops build` overwrites a tag), the runtime reports it as `<none>:<none>`. Pre-1.7.0 `cmd_info` then ran `image inspect <none>:<none>` (which fails, no such ref) and rendered the row with a red ✗ + `(not built)` label — wrong on both counts: the image *does* exist, and the user can't act on a row that gives them no actionable identifier. After 1.7.0 the discovery query now asks for `'{{.Repository}}:{{.Tag}}|{{.ID}}'` so the short-ID is available; `<none>:<none>` is rewritten to `<dangling>:<short-id>` (e.g. `<dangling>:abc123def456`); a new `ops_image_inspect_keys` map remembers the full sha256 so the subsequent `image inspect` targets the dangling image directly and the row gets its real size, date and `ops.dockerfile` label. Net result: a green ✓ row with the actionable ID for a `docker rmi` / `ops clean`. Regression guard: 4 tests in `tests/test_cmd_info_dangling.bats` (rendering shape, ✓-not-✗ marker, dockerfile label + size present, no raw `<none>:<none>` leak).

### Changed
- **`ops clean` now keeps `ops-share-*` volumes by default.** The `ops-share-nix` and `ops-share-mise` volumes are cross-container caches that often hold hours of nix-store / mise-tool downloads. Previously `clean` listed them in the volumes prompt alongside per-container volumes — a single `y` answered for ALL of them and silently nuked the cache, which several users reported as a footgun. Post-1.7.0 they're moved to a dedicated `Skipped (shared cache; pass --include-shared to drop)` sub-section under the volumes header, the summary line shows the split (`ops volumes (to prune): N` + `ops volumes (kept): M`), and the prompt only counts the to-prune list. Drop them deliberately with `clean --include-shared`. **Behaviour change**: any caller that previously relied on `ops clean` to nuke `ops-share-*` must now pass `--include-shared` explicitly.
- **`ops clean` gained `--no-volumes` / `--volumes-only` flags.** `--no-volumes` skips the volumes section + prompt entirely (script-friendly: prune dangling images and stopped ops containers without ever risking a volume rm). `--volumes-only` does the inverse — useful when you've just finished a debugging session and want to drop the per-container volumes left behind without re-listing every dangling image. The two flags are mutually exclusive (returns 2 with a diagnostic). `--dry-run` continues to compose with all of them.
- **`ops clean` interactive prompts now show the count of items at risk.** `Prune N dangling image(s) and M stopped ops container(s)? [y/N]` and `Remove K ops volume(s)? This deletes cached data (nix store, mise tools, ...) [y/N]` instead of bare yes/no questions. The prompt is also skipped entirely when its category is empty (no spurious `Prune 0 …?` question), which removes a no-op key-press from every routine `ops clean` run.
- **`ops clean` rejects unknown options** with a clear `Error: unknown option '--bogus' (see 'clean --help')` + exit 2. Previously unknown args were silently shifted off and ignored, masking typos like `--vol-only` (which a user would expect to act like `--volumes-only`).

  Coverage for all four `ops clean` items: 10 new tests in `tests/test_cmd_clean_flags.bats` (default keep-shared, summary split, `--include-shared`, `--no-volumes`, `--volumes-only`, mutual-exclusion error, unknown-flag rejection, prompt count format, prompt cached-data warning, `--help` mentions all flags). The 9 existing tests in `tests/test_clean_labels.bats` remain green (the only adjustment was making the "empty 'y' on the images prompt prunes images only" test set `MOCK_DANGLING=1`, since the prompt is now skipped when there's nothing to prune).

## [1.6.0] - 2026-04-28

### Added
- **`ops env` now lists custom exports from ops.conf** in a dedicated `Custom config exports (NOT auto-propagated to container)` section. Previously the command only showed the four hardcoded auto-propagated vars (`GITHUB_TOKEN`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`); any extra `export X=…` line the user added via `ops config secret add` (e.g. `MISTRAL_API_KEY` for a non-officially-supported agent) was invisible to `ops env`. The new section parses ops.conf for every `^export NAME=` line, filters out the auto-propagated ones to avoid duplication, and renders each remaining entry with `[set]/[unset]` status + `origin: config`. A trailing footnote spells out the contract: these vars are exported when ops.conf is sourced (so they're visible in the calling shell), but `cmd_run` does NOT automatically forward them to the container — the user must pass them via `-e KEY=VAL` / `--env-file` at run time, or open an upstream issue to add the name to `_OPS_AUTO_PROPAGATED_ENVS`. Coverage: 5 new tests in `tests/test_cmd_env.bats` (custom section render, NOT-auto-propagated explanation present, no section when ops.conf has no extras, no duplication of auto-propagated names, live-env [set] detection).

  Use case: the user runs `ops config secret add MISTRAL_API_KEY --from-env` to store a key for a third-party agent they wired manually via `--env-file`, then later wonders "did ops env capture it?". Before 1.6.0: silent no, the var was just absent from `ops env`'s output. After: explicit yes, with the caveat that they still need to forward it themselves at run time.

## [1.5.0] - 2026-04-28

### Added
- **`ops config set/get/unset` accepts bracketed associative-array keys** (e.g. `OPS_AGENT_FLAGS[claude]`, `OPS_IMAGES[debian]`, `OPS_BUILD_ARGS[arch]`). The validator's regex was widened from `^OPS_[A-Z][A-Z0-9_]*$` to a two-shape grammar: pure-scalar (`OPS_FOO`) or single-entry-of-array (`OPS_FOO[index]`). The bracketed path auto-bootstraps the surrounding `declare -A <BASE>` line when the file doesn't yet have it — bash needs the declaration before the indexed assignment, otherwise the source step would silently misparse `OPS_FOO[bar]=…` as a string-indexed access on what bash thinks is an indexed array (numeric-only indices, `bar` would coerce to `0`). Coverage: 20 tests in `tests/test_cmd_config_bracketed.bats` covering bootstrap, idempotency, in-place update, multi-entry coexistence, hyphenated indices (`OPS_IMAGES[arch-min]`), end-to-end source-roundtrip, and the four malformed-key rejection paths (bare array name, empty index `OPS_FOO[]`, dangling bracket `OPS_FOO[`, nested brackets `OPS_FOO[a[b]]`).

  Concretely: this removes the only known case where the `/ops-setup` automation skill had to bypass `ops config set` and write to `ops.conf` via direct `Edit` (the `OPS_AGENT_FLAGS[<agent>]` path it uses to wire per-agent default isolation flags). Post-1.5.0, `/ops-setup` can dispatch every config-file mutation through `ops config` for atomicity + chmod 600 + idempotency without per-array helper code.

### Changed
- **`_cfg_alias_set` / `_cfg_alias_unset` are now thin wrappers around `_cfg_set_scalar` / `_cfg_unset_scalar`** with a bracketed key (`OPS_ALIASES[<name>]`). Eliminates the ~50 lines of duplicate idempotency / declare-A bootstrap / awk substr-match logic that was sitting in the alias path before this release. Internal-only refactor — external behaviour is unchanged. The `cmd_config alias add NAME ARGV` dispatch surface is preserved as-is, so anyone who scripted against it (the `/ops-setup` skill, in particular) doesn't notice. Regression guard: the existing 56 `tests/test_cmd_config_set.bats` + `tests/test_cmd_config_secret.bats` cases all stay green after the wrapper swap.
- **`_cfg_read_scalar` / `_cfg_set_scalar` / `_cfg_unset_scalar` now use `awk`'s `substr()` instead of `~ regex` for the line-match step**. Same POSIX-portability reason that already drove `_cfg_alias_set` to substr in 1.4.0: bracketed keys would otherwise need `\[` escaping, and gawk vs mawk vs BSD awk disagree on whether `\[` is a literal `[` or a backslash followed by an opening character class. Using substr() is unambiguous across every awk variant in CI's matrix.
- **`OPS_AGENT_FLAGS` is now in `_OPS_CONFIG_ARRAY_KEYS`** so the validator's bare-name rejection (`config set OPS_AGENT_FLAGS "anything"` → "is an array — use 'config set OPS_AGENT_FLAGS[<index>]'") includes a clear, actionable diagnostic pointing at the bracketed form. Same treatment as the four other associative arrays already in that list.

## [1.4.0] - 2026-04-28

### Added
- **`ops config set/get/unset` — managed scalar edits to `~/.config/ops/ops.conf`**. Three sibling subcommands that let scripts (notably the `/ops-setup` skill) mutate the config file without re-implementing a parser. `set KEY VALUE` replaces existing `KEY=` lines in place via `awk`-then-`mv` (atomic on the same filesystem); `get KEY` reads the literal stored value (echoes nothing + exit 1 when unset, distinguishing "missing" from "empty"); `unset KEY` removes every `KEY=` line. All three are idempotent — same-value `set`s and absent-key `unset`s exit 0 with the file content unchanged (verified by sha256 in `tests/test_cmd_config_set.bats`). Validation: `KEY` must match `^OPS_[A-Z][A-Z0-9_]*$`; bash array names (`OPS_IMAGES`, `OPS_DOCKERFILES`, `OPS_CONTAINER_NAMES`, `OPS_BUILD_ARGS`, `OPS_ALIASES`) are rejected explicitly because their argv shape (`OPS_ALIASES[k]=v`) doesn't fit `set KEY VALUE` — the `alias` subcommand handles them. Newlines in `VALUE` are rejected (would break the line-based parser); double-quotes around the value escape `\` and `"` so spaces / `$` / quotes round-trip safely through `source`. The file is created with chmod 600 if absent (parent dir mkdir'd), and chmod 600 is re-asserted after every mutation — secrets may land here later (see `secret add` below).

- **`ops config alias add/remove` — managed `OPS_ALIASES[]` entries**. Symmetric to scalar set/unset but operates on the `OPS_ALIASES[name]="argv..."` associative array. `alias add NAME 'argv...'` adds or replaces an entry; `alias remove NAME` deletes it (idempotent). Adds the surrounding `declare -A OPS_ALIASES` block to the file when missing so a fresh ops.conf bootstraps cleanly. Reserved names from `_OPS_RESERVED` (built-in subcommands like `run`, `build`, `clean`, …) are rejected because `_expand_alias` skips them at dispatch time anyway — letting them through silently would surface as "alias does nothing" in user-land. Implementation detail: the `awk` line-match is done via `substr($0, 1, length(target))` instead of `~ pattern` because POSIX awk's behaviour on bracketed escapes (`\[`) is unspecified — gawk treats `\[` as a literal `[`, mawk/BSD awk may treat it as a backslash followed by an opening character class. `substr` is unambiguous across every awk in CI's matrix. Coverage: 37 tests in `tests/test_cmd_config_set.bats`.

- **`ops config secret add/list/remove` — manipulate `export NAME="..."` lines without leaking values to shell history or LLM context**. Three modes for `add`: `--from-env` reads `$NAME` from the calling shell, `--from-stdin` reads one newline-terminated line from stdin (suitable for `echo $TOKEN | ops config secret add NAME --from-stdin`), and the default interactive mode uses `read -rs` to prompt with hidden input. `list` emits names only — values are never echoed, so the output is safe to paste into a screenshot or pipe to logs. `remove NAME` is idempotent. chmod 600 is enforced after every mutation. Critical implementation detail: a `_PRE_SOURCE_ENV` snapshot is taken at the very top of `ops.sh` (before `source ops.conf` runs) so `--from-env` reads the caller's intent rather than the value the config file just re-injected via its own `export NAME=…`. Without that snapshot, rotating a token via `env NEW=… ops config secret add NAME --from-env` would silently re-write the OLD value back over the new one (ops.conf's source step had already restored `$NAME`). Coverage: 19 tests in `tests/test_cmd_config_secret.bats` covering all three modes, key validation (uppercase shell identifier shape), idempotency, value rotation, list-name-only contract (with `refute_output_contains` on the actual secret bytes), chmod 600 invariant, and an end-to-end test asserting that a secret-laden ops.conf is sourcable cleanly under the existing security guard (no "Refusing to source" / "syntax error").

- **`OPS_DEFAULT_RUN_FLAGS` — global flags injected before every `ops run` argv**. Set to e.g. `"--no-rm --no-wayland"` in ops.conf to keep containers across sessions and skip Wayland forwarding without rewriting every alias. Field-split intentionally on whitespace (tokens, not single args). Injected at the head of `cmd_run`'s argv so user CLI flags appear later and win on "last write wins" state machines (`ephemeral`, `wayland_auto`, …). Empty value is a no-op. Documented in `cmd_config --help` and exercised by 3 tests in `tests/test_default_flags.bats`.

- **`OPS_AGENT_FLAGS[<agent>]` — per-agent default flags**. Associative array keyed on `claude`, `gemini`, `opencode`, `codex`. When the user passes `--<agent>` on the command line, the new `_agent_run_extras` helper injects the matching `OPS_AGENT_FLAGS[<agent>]` tokens into the remaining argv via `set -- $tokens "$@"` so the parser processes them on the next loop turn. Lets users wire e.g. `OPS_AGENT_FLAGS[claude]="--claude-volume --install"` once and have every `--claude` invocation honour it without per-alias duplication. Coverage in `tests/test_default_flags.bats`.

- **`OPS_ISOLATION_PRESET` — coarse-grained isolation dial (host/volume/isolated/fully-isolated)**. Maps to `mount_home` and per-agent volume defaults: `host` is the legacy behaviour (HOME mounted, agent reads host config), `volume` keeps HOME mounted but routes per-agent credentials through named Docker volumes (`ops-claude`, `ops-gemini`, …), `isolated` flips `mount_home=0` so agents only see their own bind-mount slice of HOME, `fully-isolated` combines `mount_home=0` with per-agent volumes for a hermetic container. `volume` and `fully-isolated` defer to user-pinned per-agent state — if the user already passed `--claude-mount` (or `--no-claude-mount`), the preset does not override. Invalid values exit 1 with a clear diagnostic. Coverage: 6 tests in `tests/test_default_flags.bats`.

- **`ops env` — surface auto-propagated environment variables (names only)**. Lists `GITHUB_TOKEN`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY` with `[set]` / `[unset]` status and an `origin: shell|config|both` annotation that distinguishes shell-exported from ops.conf-stored vars (computed against the `_PRE_SOURCE_ENV` snapshot taken before the config file was sourced). Values are NEVER printed — `ops env` output is safe to paste into a screenshot. Useful when debugging "why is `ANTHROPIC_API_KEY` not reaching claude in the container?" — checks both layers in one call. Coverage: 7 tests in `tests/test_cmd_env.bats`.

- **`ops volume list [--agent]` — curated listing of ops-managed volumes**. Filters `volume ls --filter label=ops.volume=true` (the label `ensure_volume` stamps on every volume it creates). `--agent` further restricts to per-agent credential volumes (`ops-claude`, `ops-gemini`, `ops-opencode`, `ops-codex`). `volume`/`volumes` plural form is accepted as an alias. Raw operations (rm, inspect) are not exposed here — the user keeps using `ops runtime volume <cmd>` for the unfiltered runtime CLI. Coverage: 8 tests in `tests/test_cmd_volume.bats`.

- **`ops doctor --fix` — surface concrete remediation commands**. After the diagnostic, prints a `Suggested fixes` section listing the exact shell commands that resolve each warning (e.g. `ops -i debian build` for an unbuilt image, `ops runtime rm -f <ctn>` for an orphan container, `ops config set OPS_RUNTIME auto` for a missing config file). Suggestions only — nothing is auto-executed. Auto-execution was deliberately rejected because a blanket `runtime rm -f` triggered by a misclassified diagnostic could nuke a working container; keeping the user as the final authority is the safer default. Coverage: 7 tests in `tests/test_doctor_fix.bats`.

## [1.3.0] - 2026-04-28

### Fixed
- **`curl -fsSL .../install.sh | sh` aborted with `sh: <line>: [tag: not found`**. Under `dash` as `/bin/sh` (Debian/Ubuntu default), the HTTP-streaming reader interpreted backticks inside our comments and double-quoted `printf` format strings as command substitution, even though the bytes were either inside a `# …` line or escaped with `\``. The same script piped via `cat file | sh` never reproduced it, which kept the diagnosis off-trail for a while; we initially shipped only the `main() { … }` wrap (see Added below) and the streaming error persisted. Root fix: replaced every backtick in `install.sh` with a single quote — comments and printf strings both. Single quotes carry the same "this is a literal token, not running code" intent without exposing dash's stream-parsing edge case. Verified via real `curl|sh` against `raw.githubusercontent.com` after the push: exit 0, no parser noise. Regression guard piggy-backs on the existing `tests/test_install_sh.bats` suite (33 tests, all green); the script is now backtick-free, so any reintroduction would surface in code review.

### Added
- **`ops self-update [--check] [--force] [REF]` subcommand** — top-level wrapper around `install.sh` that updates ops-cli in place. Re-execs `$SCRIPT_DIR/install.sh` with `OPS_INSTALL_DIR=$SCRIPT_DIR` and `OPS_REF=${REF:-}` so all the resolution logic (default ref = latest `vX.Y.Z` tag, idempotent fetch+checkout, in-place upgrade/downgrade, untracked files preserved) lives in one place — no duplicate update code in `ops.sh`. Distinct from `ops nerdctl self-update` (which targets the nerdctl binary) and from `ops update [KEY]` (which rebuilds an image).
  - **`--check` / `-c` (preview mode)**: prints `current → target` summary and exits 0 without touching the filesystem. Composes with `[REF]` so the user can preview a specific switch (`ops self-update --check main`). Wired through to `install.sh` via `OPS_CHECK=1` (also usable directly under `curl|sh` — `OPS_CHECK=1 OPS_REF=v2.0.0 curl … | sh`) so the resolution logic stays single-sourced. Skips the dirty-working-tree safety check because no checkout means no risk of clobber. Action label heuristic: `install (fresh clone)` when the install dir is absent, `no-op (already at target)` when the local `git describe --tags --always` equals `REF` *or* the local HEAD SHA equals the resolved `git ls-remote` SHA (the latter mostly catches branches and full SHAs; for annotated tags `ls-remote` returns the tag-object SHA rather than the underlying commit, which is why the name match is checked first), `upgrade` otherwise. Flagged as a hint, not a guarantee — the remote ref might shift between check and run.
  - **Safety net**: refuses to run when `$SCRIPT_DIR` has uncommitted edits to tracked files, because `install.sh`'s update path runs `git checkout --force` and would silently discard them. Lists the dirty files in the error message so the user sees what would have been lost. Trigger reproduced during dev: a `./ops.sh self-update` from a contributor's clone wiped the in-flight changes that this very subcommand was being added in. Bypass with `--force` (or `-f`) when the dirty state is intentional / disposable. `git status --porcelain --untracked-files=no` is used so untracked files (which `install.sh`'s checkout preserves anyway) are not flagged.
  - **Other refusal paths**: `$SCRIPT_DIR` is not a git checkout (manual copy of `ops.sh`) or `install.sh` is missing from it (clone predates the installer). Both cases surface a reinstall hint pointing at the canonical `curl|sh` line; `--force` does NOT bypass these — re-cloning is the only safe path.
  - Coverage: 19 new bats tests in `tests/test_install_sh.bats` covering the help block (`--force` and `--check` mentions), the three refusal paths (non-git / missing-install.sh / dirty-tree), the env-var hand-off (`OPS_REF` + `OPS_INSTALL_DIR` + `OPS_CHECK`), the empty-ref auto-resolve case, the `--force` / `-f` and `--check` / `-c` bypasses, the `--force REF` argv combo, rejection of unknown flags, the four `OPS_CHECK=1` matrices (fresh / upgrade / no-op / branch SHA), and a regression guard asserting that `OPS_CHECK=1` does not mutate the install tree.

- **`install.sh` is now wrapped in `main() { ... }` invoked at end-of-file**. Defensive curl|sh pattern (rustup, oh-my-zsh, brew installer all do this): POSIX requires the entire function body to be parsed before invocation, so a truncated download — e.g. a network hiccup mid-pipe to `sh` — fails to parse `main` itself and never executes a partial install. The wrap on its own did **not** fix the `[tag: not found` symptom we were chasing (that turned out to be the backtick parsing — see Fixed above), but it remains a real defence against a different class of bug: TCP truncation. Two new bats tests in `tests/test_install_sh.bats` cover the structure (regression guard against accidentally unwrapping `main`) and the truncation case (assert that piping half the file to `sh` produces no install side effects).

- **`install.sh` summary now shows the version transition on update**. The summary line was just `ref: v1.2.0 (commit 050c147)`; it now becomes `ref: v1.0.0 → v1.2.0 (commit 050c147)` when the ref actually moved, or `ref: v1.0.0 (already up to date, commit 35cefca)` when the user re-ran the installer on the same ref. Fresh clones keep the original one-ref form (no "from" makes sense on a brand-new install). The entry line gained a `current: <ref>` annotation too, so the destination + origin are visible immediately, before the fetch + checkout actually runs. Implementation: capture `git describe --tags --always` before the checkout (only on the update path), again after, then branch the summary printf on whether they differ. Three new bats tests in `tests/test_install_sh.bats` lock the three formats.

- **`CLAUDE.md` at repo root** — release-cut runbook for assistants helping cut future tags. Documents the semver picker (PATCH vs MINOR vs MAJOR triggers), the two version sources that must stay in lockstep (`OPS_VERSION` in `ops.sh` + the `version` field in `mise/metadata.lua`), the `CHANGELOG.md` style (Keep a Changelog format, verbose bullet voice, file-path references in prose), the README-test-count sync via `scripts/check-test-counts.sh --update`, the lint+test gates to run locally, the canonical commit/tag pattern (no `Co-Authored-By` line per global preference, single clean cut commit per release), and the CI-iteration loop (amend-in-place + force-push) including the ubuntu-noble apt-installed shellcheck 0.9.0 gotcha (treats SC2015 / SC2016 info-level warnings as exit-1 under `-S style`, unlike newer 0.10+ that local dev usually has).

## [1.1.0] - 2026-04-27

### Fixed
- **`opencode` TUI hang at cold launch**. `--opencode` could never reach its TUI when launched in a freshly-installed container: opencode painted nothing, the user saw the shell apparently hang, and only `kill`+restart unstuck it. Root cause: opencode 1.14.x is shipped as a Bun single-binary that bundles its native modules into a virtual filesystem (`$bunfs`), and the `file.watcher` binding (`/$bunfs/root/watcher-*.node`) failed to extract to a real path on cold container boot — opencode logged `failed to load watcher binding` and the rendering loop never started. Fix: switched the `--opencode` install target from `github:sst/opencode` (the Bun bundle) to `npm:opencode-ai` (regular Node.js package, same upstream version). The npm distribution resolves native bindings via Node's standard mechanism and never trips the `$bunfs` extraction path. Same UX, no hang. Regression guard in `tests/test_dryrun.bats` (`run --opencode uses npm:opencode-ai (NOT github:sst/opencode)`) keeps the switch from being silently reverted.
- **`mise ERROR [nix] flake.nix … not tracked by git` lines leaked to stderr at every cold container launch** when a workdir's `mise.local.toml` declared `MISE_NIX_ALLOW_UNTRACKED=1`. Root cause: `/etc/ops-bashrc` only pre-exported `MISE_NIX_ALLOW_UNTRACKED` from `mise.local.toml` on the cache-miss path; warm sources (cache fresh) skipped the export and downstream `mise <cmd>` invocations re-tripped the nix plugin's `MiseEnv` hook before the env var reached the subprocess. The grep+export now runs on every source (cost: one `[ -f ]` + one `grep -q`, both <1 ms), so warm and cold paths both propagate the var consistently. Covered by 12 new tests in `tests/test_ops_bashrc.bats` (3 cache scenarios × pre-export + 2 negative + 3 perf + 2 pattern-tolerance + 2 helper guards) and 1 image-level test in `tests/test_image_integration.bats`.

### Performance
- **Agent warm-path launch: ~22 s → ~1 s**. `_agent_cmd` (the wrapper that powers `--claude` / `--gemini` / `--opencode` / `--codex`) now resolves the agent binary via `command -v $bin` (PATH lookup, ~0 ms) instead of `mise which $bin` (~5–17 s, full mise toolset + plugin hooks bootstrap on every invocation). The bashrc cache regen post-install (see `__ops_refresh_cache` below) ensures the install dir lands in `PATH` so the warm-path lookup resolves to the real binary, never to the mise shim. The previous `mise which` code was kept around longer than needed because we briefly thought its bootstrap side-effects were load-bearing for opencode — the real culprit was the Bun watcher binding (see Fixed above), so once `--opencode` switched to `npm:opencode-ai` the constraint vanished and the fast `command -v` path became safe again.
- **Agent 2nd-run cold-after-install: ~8 s → ~1 s**. After `mise use -g <agent>` finishes its install, it bumps the mtime of `/opt/mise/data/config/config.toml`. Without intervention, the next container launch saw `config.toml` newer than the bashrc shell-env cache and triggered a fresh `mise hook-env` cold-start (~8 s) before reaching the agent. The new `__ops_refresh_cache` helper (in `/etc/ops-bashrc`) regenerates `$PWD/.mise-nix/shell-env.cache` immediately after `mise use -g`, amortizing the regen cost into the already-slow install pass and making the very next run hit the warm path. Implementation note: the helper invokes `mise hook-env -s bash` inside a sub-shell that `unset`s `__MISE_DIFF` / `__MISE_SESSION` first, because `hook-env` only emits the diff against those vars — without the unset the cache would be re-written empty.

### Added
- **Cold-path agent install UX**. When `command -v <agent>` fails (true cold or post-`volume rm`), `_agent_cmd` now prints `==> Installing <agent> (first run, this may take a minute)...` to stderr **before** the install starts, so the user sees something during the silent ~30–60 s download/extract window. - **mise-nix plugin updates now survive the `ops-share-mise` volume overlay.** The plugin used to be copied directly into `/opt/mise/data/plugins/nix/`, which is under the volume mount point `ops-share-mise:/opt/mise/data`. Docker only populates a named volume from the image layer on its first mount; every subsequent rebuild of the plugin was therefore invisible to existing users (the stale volume copy kept masking the new image layer). The plugin now lives at `/opt/ops/mise-plugin/nix/` (outside the volume) and a symlink `/opt/mise/data/plugins/nix → /opt/ops/mise-plugin/nix` is baked in both Dockerfiles. Mise resolves the symlink transparently; every rebuild refreshes the real files and the running stack picks up the change immediately. `cmd_run` also runs `_ensure_mise_plugin_symlink` once per invocation (idempotent, ~200 ms cold) to migrate any pre-existing volume that still carries a plain plugin directory, replacing it with the symlink. `backup`/`restore`/`clean --volumes` are all transparently compatible — the symlink is preserved verbatim inside tar archives. Three new image-integration tests assert the new layout. Contributor escape hatch: `OPS_DEV_PLUGIN_MOUNT=1 ops run` bind-mounts the repo's `mise/` directory read-only over the baked path so you can iterate on Lua without rebuilding the image; two new `test_dryrun.bats` cases exercise the flag.
- **Actionable error when `flake.nix` is untracked by git.** `mise/lib/utils.lua::load_env` now checks whether `flake.nix` is tracked by git in its project root before invoking `nix print-dev-env`, and — when not — emits an explicit `git -C <root> add -fN flake.nix flake.lock` hint instead of the opaque `Failed to load environment` the user previously saw. Covers the #1 first-run trip-up: Nix flakes silently ignore untracked files in a git working tree (reproducibility guarantee), and the underlying `nix` error was never surfaced because `pcall(cmd.exec, ...)` swallowed stderr. As a secondary safety net for any *other* `nix` failure, the `nix` commands now redirect stderr to a temp file that is replayed verbatim on failure — so future users see the real diagnostic instead of the generic wrapper message.
- **Interactive shell init survives `$HOME` bind-mount.** The image used to write the mise/nix activation lines to `$HOME/.bashrc` at build time, but `ops run` bind-mounts the host's `$HOME` by default (`mount_home=1`) which shadows the image's copy. Consequence: `eval "$(mise activate bash)"`, the nix profile source, the command_not_found handler, and the PS1 were silently skipped in every interactive session — the `mise-nix` plugin's flake env hook (`[env] _.nix = true`) never made it into the PATH. The init moved to `/etc/ops-bashrc` (outside `$HOME`, survives the bind-mount). `ops run` now launches interactive shells with `bash --rcfile /etc/ops-bashrc`, and non-interactive `bash -c` agent wrappers (`--claude`, `--gemini`, `--opencode`, `--codex`, `--update`, `--nix-cleanup`, `--install -- CMD`) prepend `source /etc/ops-bashrc;` so the agent inherits the mise env (PATH / PYTHONPATH / …) from the workdir's `mise.toml` + `flake.nix`. The rcfile is guarded on `$-` (interactive vs sourced) and chains to a user-provided `$HOME/.bashrc` via an `OPS_BASHRC_DONE` recursion guard so host-side aliases still load. Five new tests in `test_dryrun.bats` and four in `test_image_integration.bats`.

Needed for `nix:google-chrome` and other unfree nixpkgs packages.
- Automatic Wayland socket forward in `ops run`: when `$WAYLAND_DISPLAY` is set and the socket exists on the host, `ops.sh` injects `-v $XDG_RUNTIME_DIR/$WAYLAND_DISPLAY:$XDG_RUNTIME_DIR/$WAYLAND_DISPLAY -e WAYLAND_DISPLAY -e XDG_RUNTIME_DIR` automatically. GUI apps like Chrome display on the host compositor out of the box. Opt out with `--no-wayland`. X11 is not auto-forwarded (considered deprecated in this project — wire it by hand if needed).
- `scripts/google-chrome.sh` wrapper, copied to `/opt/ops/bin/google-chrome` in both Dockerfiles. The image PATH is prefixed with `/opt/ops/bin` so the wrapper **shadows** the mise shim at `/opt/mise/data/shims/google-chrome`. Typing `google-chrome` manually or via any `chrome-launcher`-based tool (`chrome-devtools-mcp`, Puppeteer, Lighthouse) picks up the wrapper automatically — no `CHROME_PATH` or `--executablePath` config needed. The wrapper adds the mandatory `--no-sandbox --disable-dev-shm-usage` and, when `$WAYLAND_DISPLAY` is set, the Wayland ozone flags. It execs the real binary via absolute path from the mise install tree (`/opt/mise/data/installs/nix-google-chrome/latest/bin/google-chrome`) — the mise-nix plugin does not install into the Nix user profile, so that's the canonical location. If `google-chrome` is not installed it exits with a clear message instead of an obscure failure. Discoverable via three redundant hooks: (a) `ENV CHROME_PATH=/opt/ops/bin/google-chrome` + `PUPPETEER_EXECUTABLE_PATH=/opt/ops/bin/google-chrome`, (b) a `/usr/bin/google-chrome` symlink (fallback for tools doing `which`), and (c) a `/opt/google/chrome/chrome` symlink — the last one is specifically for `chrome-devtools-mcp` / `puppeteer-core`, which hard-code this path for the Chrome "stable" channel on Linux and ignore the env vars.
- Split mise configuration into two locations so user additions persist across container recreations: **baseline** tools (baked at build time) live in `/etc/mise/config.toml` (system-wide, read-only, re-generated on every rebuild) and **user additions** (via `ops run --claude`, `mise use -g X` inside the container, etc.) go to `/opt/mise/data/config/config.toml`, which sits inside the `ops-share-mise` volume. Mise reads both locations and merges them additively. Before this change, `mise use -g` wrote to a path inside the image layer that was wiped on every container recreation — producing "orphan" entries in `mise ls` and breaking `claude` / `terraform` / any manually-installed tool after a fresh `ops run`.
- Nix wrappers at `/opt/ops/bin/` (first in PATH, shadow the real binaries). They force `HOME=/opt/nix-home` so stateful Nix commands target the **container** profile at `/opt/nix-home/.local/state/nix/profiles/`, not the **host** profile at `/home/$user/.local/state/nix/profiles/` that was being hit because `$HOME` is bind-mounted from the host. Two scripts cover the surface:
  - `scripts/_nix-wrapper.sh` — serves `nix-env`, `nix-channel`, `nix-store`, `nix-collect-garbage` (always force HOME; legacy binaries are wholly stateful).
  - `scripts/_nix-cli-wrapper.sh` — serves `nix` (modern CLI). Forces HOME only for the stateful subcommands `profile`, `channel`, `registry`, `upgrade-nix`. Other subcommands (`build`, `shell`, `develop`, `run`, `search`, `eval`, `flake`, …) pass through transparently so the shared host-mounted `~/.cache/nix/` build cache is preserved.
  - Both wrappers accept a `--host` escape hatch to explicitly target the host profile.
  - Not wrapped: `nix-build`, `nix-shell`, `nix-instantiate`, `nix-prefetch-url` (stateless / cache-only).
- `tests/test_image_integration.bats` — integration tests that run against the actually-built `localhost/ops-dev` image (Nix discoverability + GC root, google-chrome hooks, mise config split, `/etc/machine-id`, unfree env flags, wrapper error message). Skips gracefully if Docker or the image is absent.
- CI job `image-integration` (push to `main` + `workflow_dispatch` only — not PRs, to avoid a 15-min Nix build on every review round). Builds the full Arch image and runs the integration suite.

**Fixed:**
