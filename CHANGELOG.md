## [1.13.1] - 2026-05-06

### Fixed
- **`install.sh` (and therefore `ops self-update`) silently failed to update past a tag that had been force-pushed server-side.** The bug surfaced as `ops self-update` printing only the opening line `install.sh: updating ops-cli in … (ref: vX.Y.Z, current: vY.Y.Y)` and nothing else — no summary, no `done.` marker, no error — and the local checkout staying on the old commit. Root cause: `git fetch --tags --prune --prune-tags` (without `--force`) refuses to overwrite a local tag whose server-side commit changed (e.g. when the maintainer amended a tagged release commit to fix CI). It prints `! [rejected] vY.Y.Y -> vY.Y.Y (would clobber existing tag)` on stderr but stays at exit 0 — so `set -eu` did not trip, yet the FETCH_HEAD update happened against a tag that was held back. We added `--force` to the fetch so an upstream-rewritten tag is consumed silently, matching the operational reality of how this project's release process works (see CLAUDE.md `chore: cut vX.Y.Z` block: a CI-fix amend + force-push of an annotated tag is the documented pattern).

### Added
- **Step-by-step instrumentation in `install.sh` so a future silent abort cannot mislead users.** The script now sets a `_ops_install_step` label before each milestone (`describing current HEAD`, `git fetch …`, `git checkout FETCH_HEAD`, `chmod +x ops.sh`, `symlinking …`) and an `EXIT` trap reports the active label if `set -eu` triggered exit on a non-zero status. So the previous `(silence)` failure mode now produces lines like `install.sh: aborted (exit 128) during step: git fetch vY.Y.Y (force, tags+prune)` plus a hint to re-run with `sh -x`.
- **`install.sh: done.` final marker.** Users seeing post-install noise from their shell hooks (mise activate scanning a `.mise.local.toml`, direnv reload, starship's `cmd_duration` slow-cmd warning, …) used to mistake that noise for an install failure and report bogus "self-update is broken" when it had finished cleanly. The explicit `done.` line draws a clear boundary: anything below it is from the user's shell environment, not from us. The trap above also flips a sentinel before exit so a successful run stays silent (no false-positive "aborted" message on a normal exit-0 path).

### Changed
- `cmd_update_self` (`ops self-update`) re-execs `sh install.sh` exactly as before — no behavior change in the wrapper. All the robustness improvements live in `install.sh` and apply equally to the documented `curl -fsSL .../install.sh | sh` bootstrap path used for fresh installs.

## [1.13.0] - 2026-05-06

### Performance
- **`ops run --opencode-desktop` no longer pays a ~1–2 s squashfs decompression cost on every launch.** Previous releases used `--appimage-extract-and-run`, which has AppImageKit unpack the embedded ~150 MB squashfs into `$TMPDIR/appimage_extracted_<id>/` on every invocation: `<id>` is process-instance-derived (PID + timestamp), not content-derived, so the unpacker never reuses an existing extraction even when the AppImage on disk is identical. Compounded with `ops run --rm` (the default, which makes `/tmp` a fresh tmpfs every time), this meant ~150 MB written to RAM-tmpfs and ~1–2 s of squashfs decompression burned on every single GUI launch — entirely redundant for everyone whose AppImage path hadn't changed since the previous run.

  We considered three angles. **(a)** Activating FUSE in the container (libfuse2 + `--cap-add SYS_ADMIN` + `--device /dev/fuse`) would let the AppImage self-mount the way it does on a normal Linux desktop, eliminating extraction entirely. Rejected: `CAP_SYS_ADMIN` covers ~37 sub-permissions including `mount`, `ptrace`, `setns`, `swapon/off`, `umount`, `pivot_root`, `nsenter` semantics — a non-trivial expansion of the container escape surface for a feature opt-in (see CVE-2019-5736 runc, CVE-2022-0492 cgroups, plus assorted FUSE-related path-traversal CVEs that all hinge on SYS_ADMIN being granted). The latency win does not justify the security regression. **(b)** Pre-extracting at image-build time and shipping `squashfs-root/` baked into the image. Rejected: it pins the image to a specific opencode-desktop version (defeats `mise use github:...@latest`), bumps the image size by ~150 MB whether or not the user ever launches the GUI, and rebuilding to upgrade undermines the entire point of `--opencode-desktop` as an on-demand agent. **(c)** Cache the extracted tree at runtime, on first launch, in a directory that survives container churn but is invalidated when the upstream AppImage rotates. Picked.

  Implementation: the agent_cmd inlined in the `--opencode-desktop` branch (`ops.sh:3093`) now resolves the AppImage path through `mise which opencode-desktop.AppImage` (necessary because the user-facing entry is the mise shim, whose `readlink -f` does NOT walk through to the AppImage on disk — the shim is a real bash script that `exec mise -- ...`s its way to the asset), takes a sha256-truncated fingerprint of that resolved path (`fp=$(printf '%s' "$target" | sha256sum | cut -c1-16)`), and uses it as the cache directory name (`extracted=$HOME/.cache/opencode-desktop/$fp/squashfs-root`). On cache hit the AppRun inside the cached extraction is `exec`'d directly: zero extraction, instant startup. On cache miss (first run, OR after `mise upgrade` — which moves the asset to a new sibling install path under `/opt/mise/data/installs/...`, changing the resolved path and therefore the fingerprint), a one-line message prints, the extraction runs (~3–5 s, only this once), and subsequent launches are warm. Disk usage stays bounded to the latest version's ~150 MB because we `rm -rf $HOME/.cache/opencode-desktop` (the entire parent, not just the per-fingerprint subdir) before re-extracting — old caches cannot pile up across upgrades.

  The cache lives in `$HOME/.cache/`, which is bind-mounted from the host by default (`mount_home=1`, the default `ops run` posture), so the cache survives `--rm` containers naturally with no extra volume to manage. Users running `--no-mount-home` (or `mount_home=0` via OPS_ISOLATION_PRESET=isolated) lose the cache between containers — but they also lose the AppImage itself in that mode, so there's no regression: every launch is cold either way, and the new pattern is no worse than the old.

### Changed
- The `--opencode-desktop` exec line previously read `exec opencode-desktop.AppImage --appimage-extract-and-run …`; it now reads `APPDIR="$extracted" exec "$extracted/AppRun" …` where `$extracted` is the cached squashfs-root path described above. Five flags on the binary are unchanged (`--no-sandbox`, `--ozone-platform=wayland`, `--enable-features=UseOzonePlatform`, plus the trailing `"$@"` for user args and the bracket-quoted `mise use -g` install token). The dry-run output therefore changed shape but every previously-asserted flag is still asserted: `tests/test_dryrun.bats` was updated to assert `--appimage-extract` (without the `-and-run` suffix) AND the negative `[[ "$norm" != *"--appimage-extract-and-run"* ]]` so a future revert to extract-and-run fails the test loudly. The `APPDIR=` pre-set was discovered the empirical way: opencode-desktop ships a CUSTOM `AppRun` bash wrapper (not the standard AppImageKit one) that, when `APPDIR` is unset, tries to deduce it by walking up from `$0` until it finds `$1` as a regular file. With our flags (`$1` is `--no-sandbox`), that walk never matches anything, `APPDIR` ends up empty, and the wrapper's `BIN="$APPDIR/@opencode-aidesktop"` resolves to `/@opencode-aidesktop` (root path) which doesn't exist — so `AppRun` exits with `/@opencode-aidesktop: No such file or directory`. Pre-setting `APPDIR="$extracted"` skips the broken auto-detect and lets AppRun export PATH / LD_LIBRARY_PATH / XDG_DATA_DIRS / GSETTINGS_SCHEMA_DIR relative to the cache, then exec `$APPDIR/@opencode-aidesktop` with our flags. The bats assertion now matches the exact `APPDIR="$extracted" exec "$extracted/AppRun"` substring so a future "the APPDIR= prefix is redundant, let's drop it" cleanup fires here.

### Added
- One new bats test in `tests/test_dryrun.bats`: `run --opencode-desktop caches the extracted squashfs under $HOME/.cache/opencode-desktop/`. Asserts the literal cache path expression (with `$fp` interpolation), the `sha256sum` invocation that produces the fingerprint, and the `mise which opencode-desktop.AppImage` resolution call. Locks in the cache-invalidation contract so a future refactor that drops the fingerprint and falls back to a single static path (which would let an old extraction stick around after `mise upgrade`) fails this test.

## [1.12.0] - 2026-05-06

### Fixed
- **`/opt/nix-home/.nix-profile/bin/nix: Nix binary not found` after a `latest`-tracking nix bump in the image is gone — the `nix` binary now lives at `/opt/ops/lib/nix-static`, baked into the image, never masked by the runtime `ops-share-nix` volume.** The bug surfaced as `ops run --update` exiting with three `nix:google-chrome@latest / nix:docker-client@latest / nix:docker-compose@latest: Backend install method failed: runtime error: ... Nix binary not found at /opt/nix-home/.nix-profile/bin/nix` errors plus a tail-end `_: line 4: /opt/nix-home/.nix-profile/bin/nix-collect-garbage: Aucun fichier ou dossier de ce nom`. Root cause: the user profile baked into the image (`/opt/nix-home/.nix-profile/bin/nix`) is a symlink to a `/nix/store/<hash>-nix-X.Y.Z` path; `/nix` is mounted from the persistent `ops-share-nix` volume at runtime, so when an `ops build` produced an image with a fresh nix version (different `<hash>`), the volume — frozen at the previous nix version's hash — masked the new store and the symlink resolved into nothing. The volume was right, the image was right, but the lookup-path couldn't bridge them.

  We considered five approaches before settling: (a) volume version-tagged by image digest (`ops-share-nix-<sha>`) — breaks cache on every rebuild even when nix didn't change, rejected; (b) auto-purge volume on bump detection — destroys mise-installed user packages, rejected; (c) `VOLUME /nix` directive + sync-at-build — only handles the default volume, not `--isolated-volumes`, multi-image hostile, rejected; (d) mini-shadow of the nix closure inside the image with an `ENTRYPOINT` runtime detector + `cp -an` self-heal — works but feels like a band-aid (50–100 MB image overhead, runtime magic on every container start); (e) move nix itself out of the store entirely. We picked (e). The architectural insight was that the binary nix is itself a nix package referenced by absolute `/nix/store/...` path; the bug is structurally inherent to that arrangement, and only sortir nix from the store dissolves it.

  Implementation: a new RUN block (Dockerfile §3b, mirrored in `Dockerfile.debian`) uses the bootstrap nix from `nixos.org/nix/install` to call `nix build nixpkgs#pkgsStatic.nix --no-link --print-out-paths`, which downloads the prebuilt fully-static musl-linked nix binary from `cache.nixos.org` (~25 s on warm cache, ~30 MB binary). The binary is `install`'d to `/opt/ops/lib/nix-static` (root-owned, 0755), and a symlink farm in the same directory dispatches via argv[0] for legacy commands (`nix-env -> nix-static`, `nix-store -> nix-static`, `nix-channel -> nix-static`, `nix-collect-garbage -> nix-static`, `nix-build -> nix-static`, `nix-instantiate -> nix-static`, `nix-shell -> nix-static`, `nix-prefetch-url -> nix-static`). nix's busybox-style argv[0] dispatch (verified empirically on 2.34.7 — `ln -sf nix-static nix-store && ./nix-store --version` reports `nix-store (Nix) 2.34.7`) means a single static binary serves every entry point with no per-command wrapper. The bootstrap nix in `/nix/store` remains in place during mise tool installation (it's still what `mise use -g nix:git ...` invokes, transparently), and is garbage-collected at the end of the same RUN if `NIX_CLEANUP=true`.

  The two existing wrappers `scripts/_nix-cli-wrapper.sh` (modern `nix` CLI, selective `HOME=/opt/nix-home` for stateful subcommands) and `scripts/_nix-wrapper.sh` (legacy `nix-env` / `nix-store` / `nix-channel` / `nix-collect-garbage`, always force `HOME`) had their `REAL=/opt/nix-home/.nix-profile/bin/...` line repointed to `REAL=/opt/ops/lib/nix-static` and `real=/opt/ops/lib/"$name"` respectively. Their selective HOME-rewrite logic and `--host` escape hatch are unchanged. `ops.sh` `--nix-cleanup` and `--update` had `/opt/nix-home/.nix-profile/bin/nix-collect-garbage` rewritten to `/opt/ops/lib/nix-collect-garbage` so the `--update` agent loop survives the same bug.

  Coverage: two new image-integration tests in `tests/test_image_integration.bats`. `image: nix-static is fully static (no dynamic deps)` greps `file /opt/ops/lib/nix-static` for `statically linked` — fires if a future nixpkgs revision flips the build to dynamic linking or someone switches the source URL away from `pkgsStatic`. `image: nix-static survives a stale /nix store (volume desync simulation)` is the regression guard for the actual bug: it `mv`s the store path that `/opt/nix-home/.nix-profile/bin/nix` resolves to out of the way, runs `nix --version`, expects a clean exit with `nix (Nix) ...` — i.e. asserts that the new `nix` lookup path bypasses the broken symlink chain entirely. The pre-existing tests (`image: nix binary is discoverable via PATH and reports a version`, `image: explicit GC root protects the Nix profile against collect-garbage`, `image: Nix profile binary directory exists (symlink chain resolves)`) keep passing because we deliberately leave the dynamic profile in the image — only the lookup path that ends in `nix --version` and the actual binary the wrappers call have changed.

  What stayed: the runtime `/nix` volume mount (`ops-share-nix:/nix`) — it still holds the content-addressable store of every package mise installs, which is shareable across images and survives rebuilds because CA paths don't drift when only the nix binary version changes. `ops backup ops-share-nix` / `ops restore` keep working unchanged. `--no-nix-volume` still bypasses the volume. `--isolated-volumes` still creates `${OPS_CONTAINER_NAME}-nix`. The one piece of state that no longer matters whether it's in the volume or the image is the nix binary itself, which is now image-only.

  Image-size impact: +~30 MB for `/opt/ops/lib/nix-static`. The bootstrap closure still lives in the image until `NIX_CLEANUP=true` GCs it, which is the same as today (no change to defaults).

## [1.11.0] - 2026-05-06

### Added
- **`ops run --opencode-desktop` launches the Electron GUI variant of opencode by pulling the prebuilt AppImage upstream publishes on every release.** Pre-this-change, the four `--<agent>` flags resolved to npm packages running as terminal TUIs inside the container; users wanting the desktop GUI had to install it on the host themselves and step out of the `ops run` model. The new flag closes that gap by adding a fifth agent flag wired through mise's `github:` backend with an `asset_pattern` filter (`github:sst/opencode[asset_pattern=opencode-desktop-linux-x86_64.AppImage]`), so the binary lands on the shared `ops-share-mise` volume next to claude / gemini / opencode / codex and is reused across containers without re-downloading.

  We initially tried two paths that did not work and are documented here so we don't repeat them. **First**, we routed through nixpkgs (`nix:opencode-desktop`) using the project's embedded mise-nix plugin. That installs but compiles a Tauri+Rust+WebKit2GTK build from source (~10–15 min cold cache, because Hydra hadn't built v1.14.30 yet — `cache.nixos.org` returned HTTP 404 on the expected store path) AND the resulting binary is the obsolete Tauri version: upstream switched to Electron mid-1.x (visible in `packages/desktop/electron.vite.config.ts` on `sst/opencode`), but the nixpkgs derivation (`pkgs/by-name/op/opencode-desktop`) still inherits from the old `cargo-tauri.hook` source layout. Even after a successful 15-min build, WebKit2GTK aborted at startup with `Could not create default EGL display: EGL_BAD_PARAMETER` — `libEGL.so.1` is libglvnd, which needs a vendor driver (mesa-software / nvidia / intel) on disk to dispatch to, and the container ships none. **Second**, we tried `LIBGL_ALWAYS_SOFTWARE=1` + `WEBKIT_DISABLE_DMABUF_RENDERER=1` env vars to force WebKit's software pipeline; both env vars landed correctly in the `docker exec` line, but with no Mesa drivers installed inside the container `LIBGL_ALWAYS_SOFTWARE` has nothing to fall back to, so the EGL init still failed. Switching to upstream's prebuilt Electron AppImage sidesteps both problems: Electron embeds Chromium which carries its own GPU compositor and a SwiftShader software fallback that does not depend on host Mesa drivers.

  Two implementation details that bit us and are now codified as regression guards. **AppImage launch path**: the bare AppImage refused to start with `dlopen(): error loading libfuse.so.2`. The container has no fuse2 (and we deliberately don't add `--cap-add SYS_ADMIN --device /dev/fuse` to keep the runtime requirements small). The exec line therefore appends `--appimage-extract-and-run` — AppImageKit unpacks the embedded squashfs into `/tmp/appimage_extracted_<hash>/` on each launch and runs from there. Cost: ~1–2 s extra at startup, plus accumulating `/tmp` dirs that go away with the container's tmpfs. Asserted by `tests/test_dryrun.bats::run --opencode-desktop pulls Electron AppImage via github backend`. **Bracket quoting**: mise's `[asset_pattern=…]` syntax uses square brackets, which `bash -c "…"` parses as a glob character class. The emitted command therefore single-quotes the tool spec (`mise use -g 'github:sst/opencode[asset_pattern=…]'`) so no glob expansion happens against the cwd. The tests cover the literal string, so a regression that drops the quoting (or switches the spec format) fails immediately.

  Sessions are deliberately shared with the terminal CLI: the new branch in `cmd_run` (`ops.sh:3070`) calls `_agent_run_extras opencode` (not `opencode-desktop`), so `--opencode-mount` / `--opencode-volume` / `--no-opencode-mount` continue to drive the `~/.local/share/opencode` + `~/.config/opencode` state for both the TUI and the GUI. A user starting a session in the desktop and resuming it in the terminal sees the same history without further wiring; conversely, no separate `ops-opencode-desktop` named volume is ever created. This is locked in by `tests/test_match_agent_flag.bats::--opencode-desktop --opencode-volume reuses ops-opencode (no ops-opencode-desktop volume)` — if anyone splits the state into per-frontend volumes, that test fires.

  Coverage: 3 new tests across two bats files. `tests/test_dryrun.bats` adds `run --opencode-desktop pulls Electron AppImage via github backend` (asserts the `github:sst/opencode[asset_pattern=…]` install token, the `--appimage-extract-and-run` flag, the `--no-sandbox` flag, and `exec opencode-desktop.AppImage` on the exec line — four regression guards in one test) and `run --opencode-desktop uses 'command -v opencode-desktop.AppImage' (not 'mise which')` (the same warm-path regression guard that exists for the four other agents — see lines 180–209 of the same file). `tests/test_match_agent_flag.bats` adds the volume-sharing guard described above. The implementation does NOT reuse `_agent_cmd` (which it would have for symmetry with the four other agents) because `_agent_cmd`'s `bash -c` template doesn't allow injecting binary-fixed flags like `--appimage-extract-and-run --no-sandbox` between the binary name and `"$@"` without a signature change that would touch every other agent's emitted command — inlining the bash snippet in the `--opencode-desktop` branch is local, narrower, and easier to maintain.

  Theme detection (light/dark) + dconf access also need plumbing inside the container. Out of the box, the Electron GUI launches stuck on the light theme even when the host runs dark mode, and the startup logs are flooded with `dconf-CRITICAL: unable to create directory '/run/user/<uid>/dconf'` because `dconf` cannot reach the host's session bus. We added an auto-forward of the D-Bus session bus that activates **only** when `dbus_session_auto=1` — a flag flipped exclusively by the `--opencode-desktop` branch (`ops.sh:3079`). The forward block lives next to the existing Wayland auto-forward (`ops.sh:3582-3601`) and bind-mounts the bus socket (extracted from `DBUS_SESSION_BUS_ADDRESS`'s `unix:path=…` prefix) plus three env vars: `DBUS_SESSION_BUS_ADDRESS`, `XDG_CURRENT_DESKTOP`, `DESKTOP_SESSION`. The latter two let `xdg-desktop-portal` pick the right backend (gnome / kde / hyprland / …) — without them the portal sometimes answers with stale defaults (`'default'` instead of `'prefer-dark'`) even with the bus connected. Trade-off: forwarding the session bus exposes the entire host session API to the container (notifications, secret service, screen recording portal). Acceptable for the explicit `--opencode-desktop` opt-in; never enabled for plain `ops run` shells. Coverage in `tests/test_match_agent_flag.bats`: `--opencode-desktop forwards DBUS_SESSION_BUS_ADDRESS when a session bus exists` (positive path: assert socket path + env vars in dry-run, with a real `mktemp -u` socket so the `[ -S … ]` precondition passes — the test creates the socket via Python or Perl, and skips when neither is available, mirroring the existing skip patterns in `test_image_integration.bats`) and `plain run does NOT forward DBUS_SESSION_BUS_ADDRESS` (negative path: same socket, but without `--opencode-desktop` — asserts the bus is NOT in the dry-run, locking in the "opt-in only" surface).

  Bonus: along the way we also added `--ozone-platform=wayland --enable-features=UseOzonePlatform` to the exec line. Default Electron on Linux loads the X11 Ozone backend even when `WAYLAND_DISPLAY` is set; we forward the Wayland socket but not an X11 display, so the bare AppImage exits with `Missing X server or $DISPLAY / The platform failed to initialize`. We initially tried `--ozone-platform-hint=auto` (the cleanest choice on paper, post-Electron-29) but Chromium kept loading the X11 backend on the v1.14.39 build despite Wayland being fully wired (observed empirically: socket bound, env vars set, hint=auto present, `[ERROR:ozone_platform_x11.cc:256]` still fired). Switching to the explicit `--ozone-platform=wayland` plus `--enable-features=UseOzonePlatform` (the older pre-hint incantation) is what actually pinned Chromium to the Wayland Ozone backend. Hypothetical X11 users now need to override the flag manually via trailing args after `--`; acceptable since the common case is Wayland and the override path exists.

  Fifth runtime knob beyond the FUSE-less launch and the GUI deps opt-in: **`--no-sandbox` on the exec line**. Chromium's setuid sandbox helper (`chrome-sandbox` inside the AppImage's squashfs) requires `chown root:root + chmod 4755` to function. Inside an unprivileged container the unprivileged build user cannot grant either, so the helper FATALs at startup with `The SUID sandbox helper binary was found, but is not configured correctly. Rather than run without sandboxing I'm aborting now`. Disabling the Chromium sandbox via `--no-sandbox` is the canonical workaround used by every Puppeteer / Playwright / Electron-in-CI image; the trade-off is acceptable because the container boundary is already the security perimeter we trust — the Chromium internal sandbox is redundant once the process is namespaced/cgrouped. The flag is hardcoded in the agent_cmd's `exec` line (`ops.sh:3128`) before `"$@"` so user-supplied trailing args still pass through, and the regression test in `test_dryrun.bats` asserts its presence so a future cleanup that drops it (because "the app starts now, do we still need this?") fails loudly.

- **Image baseline gains a new opt-in build arg, `OPS_DESKTOP_DEPS=true`, that bakes the Electron / Chromium runtime libs needed by `--opencode-desktop`.** The Electron AppImage links against ~21 system `.so` files at runtime — `libnspr4`, `libnss3` / `libnssutil3` / `libsmime3`, `libgtk-3`, `libgbm`, `libasound`, `libcups`, plus the X11 / at-spi / cairo / pango set pulled transitively by `gtk3`. The image baseline is deliberately headless ("CLI agents are NOT baked — installed on demand by ops.sh", see Dockerfile §1 banner), so out of the box `--opencode-desktop` exits with `error while loading shared libraries: libnspr4.so: cannot open shared object file`. We considered three resolutions: (a) bake the deps unconditionally into the baseline (would add ~80–120 MB to *every* user's image, including those who only use the terminal TUIs — rejected), (b) lazy-install via `pacman -S` inside the `--opencode-desktop` agent_cmd block at first run (fragile because the cold-vs-warm test is `command -v opencode-desktop.AppImage`, which can succeed while the runtime libs are missing — half-installed state would crash on next launch), or (c) a new opt-in build arg that mirrors the existing `EXTRA_MISE_TOOLS=nix:google-chrome` opt-in pattern. We picked (c).

  The new `ARG OPS_DESKTOP_DEPS=false` is declared next to `EXTRA_MISE_TOOLS` (`Dockerfile:101`, `Dockerfile.debian:80`). A dedicated RUN block in §1b conditionally installs `gtk3 nss nspr alsa-lib libcups mesa` on Arch and `libgtk-3-0 libnss3 libnspr4 libasound2t64 libcups2 libgbm1` on Debian, falling back to a one-line "skipped" `echo` when the ARG is `false` so the layer stays cached for the default-headless build path. The minimal package set was derived empirically from `ldd` on the extracted AppImage's `@opencode-aidesktop` Electron main binary against the v1.14.39 release — `gtk3` covers ~15 of the 21 missing libs in transitive (pango / cairo / atk / at-spi2 / libxkbcommon / libxcomposite / libxdamage / libxfixes / libxrandr / libxext / libx11 / libxcb), the other six are listed explicitly. The Debian variant uses `libasound2t64` (the time_t-transitioned ALSA package on Debian testing/trixie), not `libasound2` — bookworm-pinned forks would need to flip that name.

  Activation is the same one-liner used for `EXTRA_MISE_TOOLS`:

  ```bash
  ops config set 'OPS_BUILD_ARGS[default]' 'OPS_DESKTOP_DEPS=true'
  ops update default
  ```

  Both ARGs combine cleanly through the existing `;`-separated parser at `ops.sh:408` (`OPS_BUILD_ARGS[default]="EXTRA_MISE_TOOLS=nix:terraform;OPS_DESKTOP_DEPS=true"`). The Dockerfile header comments mention the new ARG alongside the others (`Dockerfile:33-37`, `Dockerfile.debian:16-17`), and the Arch hadolint CI job already silences the DL3008 / DL3004 warnings the new RUN block would otherwise trigger (existing ignore list, no CI config change required).

## [1.10.2] - 2026-05-05

### Fixed
- **Quitting one `ops run` session no longer kills sibling sessions attached to the same container.** Pre-fix, the first `ops run` on a given container name was a `docker run --rm -it` whose PID 1 was the user-facing process (the interactive `bash --rcfile`, or — most visibly — the `bash -c "exec opencode"` wrapper for `--claude` / `--gemini` / `--opencode` / `--codex`). Subsequent `ops run` invocations against the same container went through the `if [ -n "$running" ]` branch (`ops.sh:3105` pre-fix) and attached via `docker exec -it`. When the user quit the first session — e.g. exited an `opencode` TUI in terminal A while a `bash` session was attached in terminal B — the PID 1 process exited, the runtime tore the container down because of the `--rm`, and every `docker exec` attached to it was killed by `SIGKILL`. User-visible failure mode: `ops run --opencode` in one terminal + `ops run` (plain shell) in another, then quitting the opencode TUI silently closed the bash session in the second terminal. The bug was a direct consequence of Docker's lifecycle contract (PID 1 exit → container removal under `--rm` → all attached execs die), but the wrapper's design — making the user's own command PID 1 — meant *any* normal session exit triggered it. The cleanest workaround pre-fix was to use a different `-n <name>` for each parallel session, but most users hit the bug long before reading that recommendation.

  Post-fix, `cmd_run` switches to a **shepherd-PID-1** model. The first invocation creates the container in detached mode with `tail -f /dev/null` as its long-lived placeholder process, run under `--init` (tini) so orphan children are reaped instead of accumulating as zombies in `docker top`. The user session then attaches via `docker exec -it`. Subsequent invocations also attach via `docker exec`, exactly like before. Quitting any single session is now harmless to the others — the shepherd never exits, so the container stays alive and every other `docker exec` keeps running. The container is removed only when the **last** session unregisters AND the user did not pass `--no-rm`. Sessions track their liveness via marker files at `/tmp/ops-sessions/ops-session-<host-pid>` inside the container; a host-side EXIT trap drops the marker and, if `ephemeral=1` and the directory is now empty, calls `docker rm -f` to tear the container down. A SIGKILL that bypasses the EXIT trap leaves a marker behind; the next session's entry sweep (`_ops_sweep_orphan_sessions`) detects it via `kill -0 <host-pid>` against the host process table and removes it, so the directory eventually drains and the container can still be cleaned up. The new helpers — `_ops_register_session`, `_ops_sweep_orphan_sessions`, `_ops_cleanup_session` — live near `_match_agent_flag` in `ops.sh` and are intentionally global so the `if [ -n "$running" ]` branch (joining an existing shepherd) and the create-then-attach branch (first session) share the exact same lifecycle logic.

  Pre-1.11 containers that are already running when the user upgrades do **not** carry the new `ops.shepherd=1` label. The join branch in `cmd_run` reads that label and falls back to the legacy `exec` path (no marker bookkeeping, no post-exit cleanup) when it is absent — so an in-flight upgrade does not destabilise sessions already attached to legacy containers. Once those containers are stopped and recreated by ops ≥ 1.11, the new lifecycle takes over automatically.

  Coverage: 3 new tests in `tests/test_shepherd_lifecycle.bats` — `shepherd: container survives until the last session unregisters (ephemeral=1)` (registers two sessions, drops one, asserts the container is still running, drops the other, asserts the container is gone), `shepherd: ephemeral=0 leaves the container alive after the last session` (asserts `--no-rm` semantics), and `shepherd: orphan sweep drops markers whose host PID is dead` (registers an orphan marker for an already-exited host PID and asserts the sweep removes it while sparing live markers). The tests skip cleanly when no runtime is available (mirroring the `require_ops_image` gate used by `test_image_integration.bats`) and use a vanilla `alpine:latest tail -f /dev/null` shepherd so they don't require the heavy `localhost/ops-dev` image to be built. Two existing tests were adjusted to the new lifecycle: `tests/test_flags.bats` (`run --no-rm omits --rm`) now asserts `run -d` + `exec -it` instead of `run -it`, and `tests/test_edge_cases.bats` (`empty invocation (no args) still starts bash in container`) now asserts `bash` lands in the `exec` log line, not the `run` line.

### Changed
- **`ops run` lifecycle is now multi-session-aware: shepherd PID 1 + per-session `docker exec`.** Effective `docker` invocations have changed shape — `--dry-run` now prints two commands (the detached shepherd creation, then the interactive attach) instead of one, and the existing `ops.cmdline.real` label still records the single shepherd-creation line. `--rm` continues to mean "tear the container down at the end" but the trigger moved from "PID 1 exit" to "last session exits"; `--no-rm` continues to mean "leave the container alive" and now naturally enables explicit re-attach via plain `ops run` later. The `--user`, `--workdir`, `--env TERM`, `--env COLORTERM`, and `--env MISE_TRUSTED_CONFIG_PATHS` arguments moved from `docker run` to `docker exec` because they are per-session settings; volumes, ports, runtime-passthrough flags (`--cap-add`, `--device`, …), `--env HOME`, the OCI labels, and Wayland forwarding stay on the shepherd creation line because they are container-level. `--init` is unconditionally added so PID-1 zombie reaping is correct under `tail -f /dev/null` (which is not a real init).

## [1.10.0] - 2026-04-30

### Added
- **Runtime-passthrough flags on `ops run`: `--group-add`, `--cap-add`, `--cap-drop`, `--security-opt`, `--device`, `--privileged`.** These six flags are forwarded verbatim to `<runtime> run` (docker / podman / nerdctl) before the image ref. Pre-fix, every one of these triggered the "unknown flag — passing as command" warning at `ops.sh` line ~2966 and broke the run at exec time: the runtime tried to `exec` the flag name as a binary and failed with "executable file not found in $PATH". User-visible failure mode: `ops docker` (the rootful-socket alias documented in `docs/nested-containers.md` that needs `--group-add <docker-gid>`) errored on every invocation with `docker: Error response from daemon: failed to create task ... exec: "--group-add": executable file not found`. Same class of failure for the containerd alias body, which uses `--cap-add SYS_ADMIN`, `--cap-add NET_ADMIN`, `--security-opt apparmor=unconfined`. The aliases were correct as documented; the wrapper just didn't know about the flags.

  Post-fix, these six flags are explicit case branches in `cmd_run`'s parser (alongside `-v` / `-e` / `-p` / `--no-rm` / etc.) that append to a new `extra_runtime_flags=()` array, which is then forwarded into the `args=()` composition right after `extra_envs` and `extra_ports`. The forwarding is verbatim — no normalization, no value validation — so docker/podman/nerdctl handle parsing in their own conventions (`--cap-add SYS_ADMIN` and `--cap-add=SYS_ADMIN` both work). The set is **explicit** rather than a generic "any unknown flag → passthrough" because that would silently break the existing contract where the first unknown flag terminates parsing (so the user's COMMAND remains reachable). Adding to the set is the documented extension point — see `docs/nested-containers.md` for the use case that motivated this round.

  When the container is already running, runtime-creation flags can't be applied retroactively (they're create-time only). Mirroring the existing behavior for unmounted volumes, the wrapper now prompts to recreate the container when `extra_runtime_flags` is non-empty AND the container is running. Same `[Y/n]` UX as the volume re-create prompt (`ops.sh:3091-3120`-ish before the new branch), so users get one consistent recreation flow whether they passed new mounts, new caps, or both.

  Coverage: 17 new tests in `tests/test_runtime_passthrough_flags.bats` — single-flag forwarding (`--group-add`, `--cap-add`, `--cap-drop`, `--security-opt`, `--device`, `--privileged`), repeatability (`--cap-add SYS_ADMIN --cap-add NET_ADMIN` for the containerd recipe; `--group-add 999 --group-add docker` mixing numeric and named groups), composition with `--` and an explicit command, and an end-to-end pin of `ops_alias_docker` from `docs/nested-containers.md` rendering the rootful-socket invocation cleanly. Plus a regression test that truly unknown flags still trigger the existing "passing as command" warning so the safety net for typos is preserved.

- **`-u UID:GID` / `--uid UID:GID` / `--user UID:GID` accept a colon-joined value.** Previously `-u` / `--uid` only accepted a single UID; the GID was set separately via `-g` / `--gid`. The docker / podman / nerdctl idiom is `--user UID:GID` in one token (used by the containerd nested-container alias which needs `--user 0:0` to enter the container as root for the privileged-namespace recipe). Post-fix, when the value contains `:`, the parser splits on the first colon and routes to `OPS_USER_UID` / `OPS_USER_GID`. The bare-UID form is unchanged. `--user` is a new alias for `-u` / `--uid` (matches the runtime-side flag name; harmonizes with the documented `ops` alias bodies). Closing the gap: `ops -r podman run --claude` is now equivalent to `OPS_RUNTIME=podman ops run --claude`, both work for ad-hoc per-invocation overrides without touching the persistent config. The flag is parsed in both `_parse_global_flags` (so `ops -r RUNTIME <subcmd> ...` works for all subcommands) AND in `cmd_run`'s flag parser (so `ops run -r RUNTIME ...` also works, matching the per-subcommand pattern of `-n` / `-i` / `-f` / `-H`).   Coverage: 7 new tests in `tests/test_runtime_flag.bats` — global form (`ops -r docker run` overrides `OPS_RUNTIME=podman` from env), long form (`--runtime`), per-run form (`ops run -r docker`), unset-env clean run (`-r` works with no `OPS_RUNTIME` in env), unknown-runtime exits 1, and `-r auto` resolves to the priority-first detected runtime.

## [1.5.0] - 2026-04-28

### Added
- **`ops config set/get/unset` accepts bracketed associative-array keys** (e.g. `OPS_AGENT_FLAGS[claude]`, `OPS_IMAGES[debian]`, `OPS_BUILD_ARGS[arch]`). The validator's regex was widened from `^OPS_[A-Z][A-Z0-9_]*$` to a two-shape grammar: pure-scalar (`OPS_FOO`) or single-entry-of-array (`OPS_FOO[index]`). The bracketed path auto-bootstraps the surrounding `declare -A <BASE>` line when the file doesn't yet have it — bash needs the declaration before the indexed assignment, otherwise the source step would silently misparse `OPS_FOO[bar]=…` as a string-indexed access on what bash thinks is an indexed array (numeric-only indices, `bar` would coerce to `0`). Coverage: 20 tests in `tests/test_cmd_config_bracketed.bats` covering bootstrap, idempotency, in-place update, multi-entry coexistence, hyphenated indices (`OPS_IMAGES[arch-min]`), end-to-end source-roundtrip, and the four malformed-key rejection paths (bare array name, empty index `OPS_FOO[]`, dangling bracket `OPS_FOO[`, nested brackets `OPS_FOO[a[b]]`).

  Concretely: this removes the only known case where the `/ops-setup` automation skill had to bypass `ops config set` and write to `ops.conf` via direct `Edit` (the `OPS_AGENT_FLAGS[<agent>]` path it uses to wire per-agent default isolation flags). Post-1.5.0, `/ops-setup` can dispatch every config-file mutation through `ops config` for atomicity + chmod 600 + idempotency without per-array helper code.

### Changed
- **`_cfg_alias_set` / `_cfg_alias_unset` are now thin wrappers around `_cfg_set_scalar` / `_cfg_unset_scalar`** with a bracketed key (`OPS_ALIASES[<name>]`). Eliminates the ~50 lines of duplicate idempotency / declare-A bootstrap / awk substr-match logic that was sitting in the alias path before this release. Internal-only refactor — external behaviour is unchanged. The `cmd_config alias add NAME ARGV` dispatch surface is preserved as-is, so anyone who scripted against it (the `/ops-setup` skill, in particular) doesn't notice. Regression guard: the existing 56 `tests/test_cmd_config_set.bats` + `tests/test_cmd_config_secret.bats` cases all stay green after the wrapper swap.
- **`_cfg_read_scalar` / `_cfg_set_scalar` / `_cfg_unset_scalar` now use `awk`'s `substr()` instead of `~ regex` for the line-match step**. Same POSIX-portability reason that already drove `_cfg_alias_set` to substr in 1.4.0: bracketed keys would otherwise need `\[` escaping, and gawk vs mawk vs BSD awk disagree on whether `\[` is a literal `[` or a backslash followed by an opening character class. Using substr() is unambiguous across every awk variant in CI's matrix.

## [1.4.0] - 2026-04-28

### Added
- **`ops config set/get/unset` — managed scalar edits to `~/.config/ops/ops.conf`**. Three sibling subcommands that let scripts (notably the `/ops-setup` skill) mutate the config file without re-implementing a parser. `set KEY VALUE` replaces existing `KEY=` lines in place via `awk`-then-`mv` (atomic on the same filesystem); `get KEY` reads the literal stored value (echoes nothing + exit 1 when unset, distinguishing "missing" from "empty"); `unset KEY` removes every `KEY=` line. All three are idempotent — same-value `set`s and absent-key `unset`s exit 0 with the file content unchanged (verified by sha256 in `tests/test_cmd_config_set.bats`). Validation: `KEY` must match `^OPS_[A-Z][A-Z0-9_]*$`; bash array names (`OPS_IMAGES`, `OPS_DOCKERFILES`, `OPS_CONTAINER_NAMES`, `OPS_BUILD_ARGS`, `OPS_ALIASES`) are rejected explicitly because their argv shape (`OPS_ALIASES[k]=v`) doesn't fit `set KEY VALUE` — the `alias` subcommand handles them. Newlines in `VALUE` are rejected (would break the line-based parser); double-quotes around the value escape `\` and `"` so spaces / `$` / quotes round-trip safely through `source`. The file is created with chmod 600 if absent (parent dir mkdir'd), and chmod 600 is re-asserted after every mutation — secrets may land here later (see `secret add` below).

- **`ops config alias add/remove` — managed `OPS_ALIASES[]` entries**. Symmetric to scalar set/unset but operates on the `OPS_ALIASES[name]="argv..."` associative array. `alias add NAME 'argv...'` adds or replaces an entry; `alias remove NAME` deletes it (idempotent). Adds the surrounding `declare -A OPS_ALIASES` block to the file when missing so a fresh ops.conf bootstraps cleanly. Reserved names from `_OPS_RESERVED` (built-in subcommands like `run`, `build`, `clean`, …) are rejected because `_expand_alias` skips them at dispatch time anyway — letting them through silently would surface as "alias does nothing" in user-land. Implementation detail: the `awk` line-match is done via `substr($0, 1, length(target))` instead of `~ pattern` because POSIX awk's behaviour on bracketed escapes (`\[`) is unspecified — gawk treats `\[` as a literal `[`, mawk/BSD awk may treat it as a backslash followed by an opening character class. `substr` is unambiguous across every awk in CI's matrix. Coverage: 37 tests in `tests/test_cmd_config_set.bats`.

- **`ops config secret add/list/remove` — manipulate `export NAME="..."` lines without leaking values to shell history or LLM context**. Three modes for `add`: `--from-env` reads `$NAME` from the calling shell, `--from-stdin` reads one newline-terminated line from stdin (suitable for `echo $TOKEN | ops config secret add NAME --from-stdin`), and the default interactive mode uses `read -rs` to prompt with hidden input. `list` emits names only — values are never echoed, so the output is safe to paste into a screenshot or pipe to logs. `remove NAME` is idempotent. chmod 600 is enforced after every mutation. Critical implementation detail: a `_PRE_SOURCE_ENV` snapshot is taken at the very top of `ops.sh` (before `source ops.conf` runs) so `--from-env` reads the caller's intent rather than the value the config file just re-injected via its own `export NAME=…`. Without that snapshot, rotating a token via `env NEW=… ops config secret add NAME --from-env` would silently re-write the OLD value back over the new one (ops.conf's source step had already restored `$NAME`). Coverage: 19 tests in `tests/test_cmd_config_secret.bats` covering all three modes, key validation (uppercase shell identifier shape), idempotency, value rotation, list-name-only contract (with `refute_output_contains` on the actual secret bytes), chmod 600 invariant, and an end-to-end test asserting that a secret-laden ops.conf is sourcable cleanly under the existing security guard (no "Refusing to source" / "syntax error").

- **`OPS_DEFAULT_RUN_FLAGS` — global flags injected before every `ops run` argv**. Set to e.g. `"--no-rm --no-wayland"` in ops.conf to keep containers across sessions and skip Wayland forwarding without rewriting every alias. Field-split intentionally on whitespace (tokens, not single args). Injected at the head of `cmd_run`'s argv so user CLI flags appear later and win on "last write wins" state machines (`ephemeral`, `wayland_auto`, …). Empty value is a no-op. Documented in `cmd_config --help` and exercised by 3 tests in `tests/test_default_flags.bats`.

- **`OPS_AGENT_FLAGS[<agent>]` — per-agent default flags**. Associative array keyed on `claude`, `gemini`, `opencode`, `codex`. When the user passes `--<agent>` on the command line, the new `_agent_run_extras` helper injects the matching `OPS_AGENT_FLAGS[<agent>]` tokens into the remaining argv via `set -- $tokens "$@"` so the parser processes them on the next loop turn. Lets users wire e.g. `OPS_AGENT_FLAGS[claude]="--claude-volume --install"` once and have every `--claude` invocation honour it without per-alias duplication. Coverage in `tests/test_default_flags.bats`.

- **`OPS_ISOLATION_PRESET` — coarse-grained isolation dial (host/volume/isolated/fully-isolated)**. Maps to `mount_home` and per-agent volume defaults: `host` is the legacy behaviour (HOME mounted, agent reads host config), `volume` keeps HOME mounted but routes per-agent credentials through named Docker volumes (`ops-claude`, `ops-gemini`, …), `isolated` flips `mount_home=0` so agents only see their own bind-mount slice of HOME, `fully-isolated` combines `mount_home=0` with per-agent volumes for a hermetic container. `volume` and `fully-isolated` defer to user-pinned per-agent state — if the user already passed `--claude-mount` (or `--no-claude-mount`), the preset does not override. Invalid values exit 1 with a clear diagnostic. Coverage: 6 tests in `tests/test_default_flags.bats`.

- **`ops env` — surface auto-propagated environment variables (names only)**. Lists `GITHUB_TOKEN`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY` with `[set]` / `[unset]` status and an `origin: shell|config|both` annotation that distinguishes shell-exported from ops.conf-stored vars (computed against the `_PRE_SOURCE_ENV` snapshot taken before the config file was sourced). Values are NEVER printed — `ops env` output is safe to paste into a screenshot. Useful when debugging "why is `ANTHROPIC_API_KEY` not reaching claude in the container?" — checks both layers in one call. Coverage: 7 tests in `tests/test_cmd_env.bats`.

- **`ops volume list [--agent]` — curated listing of ops-managed volumes**. Filters `volume ls --filter label=ops.volume=true` (the label `ensure_volume` stamps on every volume it creates). `--agent` further restricts to per-agent credential volumes (`ops-claude`, `ops-gemini`, `ops-opencode`, `ops-codex`). `volume`/`volumes` plural form is accepted as an alias. Raw operations (rm, inspect) are not exposed here — the user keeps using `ops runtime volume <cmd>` for the unfiltered runtime CLI. Coverage: 8 tests in `tests/test_cmd_volume.bats`.

- **`ops doctor --fix` — surface concrete remediation commands**. After the diagnostic, prints a `Suggested fixes` section listing the exact shell commands that resolve each warning (e.g. `ops -i debian build` for an unbuilt image, `ops runtime rm -f <ctn>` for an orphan container, `ops config set OPS_RUNTIME auto` for a missing config file). Suggestions only — nothing is auto-executed. Auto-execution was deliberately rejected because a blanket `runtime rm -f` triggered by a misclassified diagnostic could nuke a working container; keeping the user as the final authority is the safer default. Coverage: 7 tests in `tests/test_doctor_fix.bats`.

## [1.3.0] - 2026-04-28

### Fixed
- **`curl -fsSL .../install.sh | sh` aborted with `sh: <line>: [tag: not found`**. Under `dash` as `/bin/sh` (Debian/Ubuntu default), the HTTP-streaming reader interpreted backticks inside our comments and double-quoted `printf` format strings as command substitution, even though the bytes were either inside a `# …` line or escaped with `\``. The same script piped via `cat file | sh` never reproduced it, which kept the diagnosis off-trail for a while; we initially shipped only the `main() { … }` wrap (see Added below) and the streaming error persisted. Root fix: replaced every backtick in `install.sh` with a single quote — comments and printf strings both. Single quotes carry the same "this is a literal token, not running code" intent without exposing dash's stream-parsing edge case. Verified via real `curl|sh` against `raw.githubusercontent.com` after the push: exit 0, no parser noise. Regression guard piggy-backs on the existing `tests/test_install_sh.bats` suite (33 tests, all green); the script is now backtick-free, so any reintroduction would surface in code review.

### Added
- **`ops self-update [--check] [--force] [REF]` subcommand** — top-level wrapper around `install.sh` that updates ops-cli in place. Re-execs `$SCRIPT_DIR/install.sh` with `OPS_INSTALL_DIR=$SCRIPT_DIR` and `OPS_REF=${REF:-}` so all the resolution logic (default ref = latest `vX.Y.Z` tag, idempotent fetch+checkout, in-place upgrade/downgrade, untracked files preserved) lives in one place — no duplicate update code in `ops.sh`. Distinct from `ops nerdctl self-update` (which targets the nerdctl binary) and from `ops update [KEY]` (which rebuilds an image).
  - **`--check` / `-c` (preview mode)**: prints `current → target` summary and exits 0 without touching the filesystem. Composes with `[REF]` so the user can preview a specific switch (`ops self-update --check main`). Wired through to `install.sh` via `OPS_CHECK=1` (also usable directly under `curl|sh` — `OPS_CHECK=1 OPS_REF=v2.0.0 curl … | sh`) so the resolution logic stays single-sourced. Skips the dirty-working-tree safety check because no checkout means no risk of clobber. Action label heuristic: `install (fresh clone)` when the install dir is absent, `no-op (already at target)` when the local `git describe --tags --always` equals `REF` *or* the local HEAD SHA equals the resolved `git ls-remote` SHA (the latter mostly catches branches and full SHAs; for annotated tags `ls-remote` returns the tag-object SHA rather than the underlying commit, which is why the name match is checked first), `upgrade` otherwise. Flagged as a hint, not a guarantee — the remote ref might shift between check and run.
  - **Safety net**: refuses to run when `$SCRIPT_DIR` has uncommitted edits to tracked files, because `install.sh`'s update path runs `git checkout --force` and would silently discard them. Lists the dirty files in the error message so the user sees what would have been lost. Trigger reproduced during dev: a `./ops.sh self-update` from a contributor's clone wiped the in-flight changes that this very subcommand was being added in. Bypass with `--force` (or `-f`) when the dirty state is intentional / disposable. `git status --porcelain --untracked-files=no` is used so untracked files (which `install.sh`'s checkout preserves anyway) are not flagged.
  - **Other refusal paths**: `$SCRIPT_DIR` is not a git checkout (manual copy of `ops.sh`) or `install.sh` is missing from it (clone predates the installer). Both cases surface a reinstall hint pointing at the canonical `curl|sh` line; `--force` does NOT bypass these — re-cloning is the only safe path.
  - Coverage: 19 new bats tests in `tests/test_install_sh.bats` covering the help block (`--force` and `--check` mentions), the three refusal paths (non-git / missing-install.sh / dirty-tree), the env-var hand-off (`OPS_REF` + `OPS_INSTALL_DIR` + `OPS_CHECK`), the empty-ref auto-resolve case, the `--force` / `-f` and `--check` / `-c` bypasses, the `--force REF` argv combo, rejection of unknown flags, the four `OPS_CHECK=1` matrices (fresh / upgrade / no-op / branch SHA), and a regression guard asserting that `OPS_CHECK=1` does not mutate the install tree.

- **`install.sh` is now wrapped in `main() { ... }` invoked at end-of-file**. Defensive curl|sh pattern (rustup, oh-my-zsh, brew installer all do this): POSIX requires the entire function body to be parsed before invocation, so a truncated download — e.g. a network hiccup mid-pipe to `sh` — fails to parse `main` itself and never executes a partial install. The wrap on its own did **not** fix the `[tag: not found` symptom we were chasing (that turned out to be the backtick parsing — see Fixed above), but it remains a real defence against a different class of bug: TCP truncation. Two new bats tests in `tests/test_install_sh.bats` cover the structure (regression guard against accidentally unwrapping `main`) and the truncation case (assert that piping half the file to `sh` produces no install side effects).

- **`install.sh` summary now shows the version transition on update**. The summary line was just `ref: v1.2.0 (commit 050c147)`; it now becomes `ref: v1.0.0 → v1.2.0 (commit 050c147)` when the ref actually moved, or `ref: v1.0.0 (already up to date, commit 35cefca)` when the user re-ran the installer on the same ref. Fresh clones keep the original one-ref form (no "from" makes sense on a brand-new install). The entry line gained a `current: <ref>` annotation too, so the destination + origin are visible immediately, before the fetch + checkout actually runs. Implementation: capture `git describe --tags --always` before the checkout (only on the update path), again after, then branch the summary printf on whether they differ. Three new bats tests in `tests/test_install_sh.bats` lock the three formats.

- **`CLAUDE.md` at repo root** — release-cut runbook for assistants helping cut future tags. Documents the semver picker (PATCH vs MINOR vs MAJOR triggers), the two version sources that must stay in lockstep (`OPS_VERSION` in `ops.sh` + the `version` field in `mise/metadata.lua`), the `CHANGELOG.md` style (Keep a Changelog format, verbose bullet voice, file-path references in prose), the README-test-count sync via `scripts/check-test-counts.sh --update`, the lint+test gates to run locally, the canonical commit/tag pattern (no `Co-Authored-By` line per global preference, single clean cut commit per release), and the CI-iteration loop (amend-in-place + force-push) including the ubuntu-noble apt-installed shellcheck 0.9.0 gotcha (treats SC2015 / SC2016 info-level warnings as exit-1 under `-S style`, unlike newer 0.10+ that local dev usually has).

## [1.1.0] - 2026-04-27

### Fixed
- **`opencode` TUI hang at cold launch**. `--opencode` could never reach its TUI when launched in a freshly-installed container: opencode painted nothing, the user saw the shell apparently hang, and only `kill`+restart unstuck it. Root cause: opencode 1.14.x is shipped as a Bun single-binary that bundles its native modules into a virtual filesystem (`$bunfs`), and the `file.watcher` binding (`/$bunfs/root/watcher-*.node`) failed to extract to a real path on cold container boot — opencode logged `failed to load watcher binding` and the rendering loop never started. Fix: switched the `--opencode` install target from `github:sst/opencode` (the Bun bundle) to `npm:opencode-ai` (regular Node.js package, same upstream version). The npm distribution resolves native bindings via Node's standard mechanism and never trips the `$bunfs` extraction path. Same UX, no hang. Regression guard in `tests/test_dryrun.bats` (`run --opencode uses npm:opencode-ai (NOT github:sst/opencode)`) keeps the switch from being silently reverted.
- **`mise ERROR [nix] flake.nix … not tracked by git` lines leaked to stderr at every cold container launch** when a workdir's `mise.local.toml` declared `MISE_NIX_ALLOW_UNTRACKED=1`. Root cause: `/etc/ops-bashrc` only pre-exported `MISE_NIX_ALLOW_UNTRACKED` from `mise.local.toml` on the cache-miss path; warm sources (cache fresh) skipped the export and downstream `mise <cmd>` invocations re-tripped the nix plugin's `MiseEnv` hook before the env var reached the subprocess. The grep+export now runs on every source (cost: one `[ -f ]` + one `grep -q`, both <1 ms), so warm and cold paths both propagate the var consistently. Covered by 12 new tests in `tests/test_ops_bashrc.bats` (3 cache scenarios × pre-export + 2 negative + 3 perf + 2 pattern-tolerance + 2 helper guards) and 1 image-level test in `tests/test_image_integration.bats`.

### Performance
- **Agent warm-path launch: ~22 s → ~1 s**. `_agent_cmd` (the wrapper that powers `--claude` / `--gemini` / `--opencode` / `--codex`) now resolves the agent binary via `command -v $bin` (PATH lookup, ~0 ms) instead of `mise which $bin` (~5–17 s, full mise toolset + plugin hooks bootstrap on every invocation). The bashrc cache regen post-install (see `__ops_refresh_cache` below) ensures the install dir lands in `PATH` so the warm-path lookup resolves to the real binary, never to the mise shim. The previous `mise which` code was kept around longer than needed because we briefly thought its bootstrap side-effects were load-bearing for opencode — the real culprit was the Bun watcher binding (see Fixed above), so once `--opencode` switched to `npm:opencode-ai` the constraint vanished and the fast `command -v` path became safe again.
- **Agent 2nd-run cold-after-install: ~8 s → ~1 s**. After `mise use -g <agent>` finishes its install, it bumps the mtime of `/opt/mise/data/config/config.toml`. Without intervention, the next container launch saw `config.toml` newer than the bashrc shell-env cache and triggered a fresh `mise hook-env` cold-start (~8 s) before reaching the agent. The new `__ops_refresh_cache` helper (in `/etc/ops-bashrc`) regenerates `$PWD/.mise-nix/shell-env.cache` immediately after `mise use -g`, amortizing the regen cost into the already-slow install pass and making the very next run hit the warm path. Implementation note: the helper invokes `mise hook-env -s bash` inside a sub-shell that `unset`s `__MISE_DIFF` / `__MISE_SESSION` first, because `hook-env` only emits the diff against those vars — without the unset the cache would be re-written empty.

- **Cold-path agent install UX**. When `command -v <agent>` fails (true cold or post-`volume rm`), `_agent_cmd` now prints `==> Installing <agent> (first run, this may take a minute)...` to stderr **before** the install starts, so the user sees something during the silent ~30–60 s download/extract window. Previously most call sites used `sprintf`-style `"%s"` with double quotes — safe on typical paths but vulnerable to shell metacharacters if a tool name, store path, or flake ref ever contained one. Low real-world risk (inputs come from the user's own mise config / the Nix store), but eliminates a class of latent injections. `vscode.lua` in particular went from 9 unquoted interpolations to zero.

Previously some branches fell back to `"$@"`, which would have re-introduced `--host` into the real binary's argv if the detection loop were later extended. Cosmetic today, defensive for future edits.

The init moved to `/etc/ops-bashrc` (outside `$HOME`, survives the bind-mount). `ops run` now launches interactive shells with `bash --rcfile /etc/ops-bashrc`, and non-interactive `bash -c` agent wrappers (`--claude`, `--gemini`, `--opencode`, `--codex`, `--update`, `--nix-cleanup`, `--install -- CMD`) prepend `source /etc/ops-bashrc;` so the agent inherits the mise env (PATH / PYTHONPATH / …) from the workdir's `mise.toml` + `flake.nix`.
