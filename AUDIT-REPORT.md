## HIGH (2)

### `src/config/manage.rs:178` — config set writes every value as a TOML string, so setting a boolean schema key invalidates the whole layer and silently reverts a filtering network posture
*bug*

**Scénario :** manage::set always inserts a string (`value(val)` where val: &str), and main.rs config_set (line 1969) passes any dotted key through with no type awareness. The schema has boolean-typed leaves: NetworkTable.stats and NetworkTable.ask_notice are Option<bool> (schema.rs:369,374). Concrete failure: a project has a trusted `[network] mode = "deny"` allowlist; the user runs the natural `ops config set network.stats false` (stats is a documented knob: "off via [network] stats = false"). set writes `stats = "false"` (a string). On the next load, serde fails NetworkTable (string != bool), the untagged NetworkField then fails both variants, the whole RawConfig parse errors, and the loader drops the ENTIRE project layer with only a stderr warning — the deny allowlist, secrets, binds all vanish and the launch runs with the default `shared` network (full host egress for the agent). The accepted whole-layer-drop residual covers hand-authored wrong types; here ops's own write verb manufactures the invalid type, and `config set` even reports success. Fix direction: type the write for known non-string leaves (parse booleans/integers for schema keys, or refuse keys whose schema type is not string, mirroring the NotScalar refusal), or validate the resulting document re-parses as RawConfig before writing.

**Vérif :** Traced the full chain: manage::set (manage.rs:202-231) writes every value as a TOML string (value(val)/Value::from(&str)) with no type awareness in main.rs config_set (1955-2010), so `ops config set network.stats false` — stats being a documented Option<bool> knob (schema.rs:395, help.rs:743) — produces `stats = "false"`. On the next load the untagged NetworkField (schema.rs:362) fails both variants, schema::parse errors, and read_project drops the ENTIRE project layer with only an "ignoring <path>" stderr warning (mod.rs:2990-2996), reverting the network to the default Shared (mod.rs:480) — full host egress where a trusted deny allowlist stood — while config set reported success and even `--trust` re-blessed the unparseable file. This is distinct from the accepted hand-authored wrong-type residual (ops's own verb manufactures the invalid type and the revert is fail-open, not fail-closed); the only flaw is the line anchor (178 is `get`, the defect is in `set` at ~202-231), which does not change the substance.

### `src/main.rs:571` — `ops trust <path> --show` silently records trust instead of showing it
*bug*

**Scénario :** trust_cmd checks only the FIRST argument for --show: `if first.as_deref().and_then(|s| s.to_str()) == Some("--show")`. With the common flag-after-positional order, `ops trust ./cloned-repo/.ops.toml --show` takes the path as `first`, never matches --show, and falls through to record_trust() — the trailing --show is silently discarded. Failure scenario: a user inspecting an untrusted cloned repo runs `ops trust .ops.toml --show` to QUERY its state; ops instead vouches for the file, so its security fields (binds, network allowlist, secrets, nixpkgs pin) become honored at the next launch. This inverts a read-only query into the single most security-sensitive write in the tool, with only a 'trusted' confirmation line to notice. Extra/unknown arguments to trust/untrust should be rejected (exit 2), and --show should be recognized in any position.

**Vérif :** Traced src/main.rs:568-575: trust_cmd tests only the FIRST arg for "--show" and otherwise calls record_trust(config_path_arg(first)), silently dropping remaining args — so `ops trust <path> --show` records trust instead of showing it, exactly as claimed; dispatch at line 66 passes raw args with no other parsing. This violates the repo's own convention (sibling dispatchers like stop_cmd parse flags in any position and reject unknown tokens with exit 2) on the single most security-sensitive write in the tool, and the green "ops: trusted <path>" confirmation plausibly reads as the query's answer. High severity is honest: the trigger is a common flag-after-positional habit on the exact inspect-an-untrusted-repo workflow, and the consequence is honoring that config's binds/network/secrets/nixpkgs at the next launch.

*bug*

**Scénario :** The parent traversal in get (`table.get(seg).and_then(Item::as_table)`), unset (line 221, as_table_mut), and set (line 186-189) only descends Item::Table; an inline table is Item::Value(Value::InlineTable), for which as_table/as_table_mut return None. **Vérif :** Traced directly: manage.rs get (line 185), set (lines 209-213), and unset (line 245) all traverse parents via Item::as_table/as_table_mut, which in toml_edit 0.22 return None for an inline table (Item::Value(Value::InlineTable) — verified in the crate source, item.rs:89-121). ### `src/sandbox/cgroup.rs:191` — Resource limits silently skipped for SSH/TTY login sessions (delegated_controllers only finds /user@ under the user-manager tree)
*bug*

**Scénario :** delegated_controllers() locates the delegation root by searching the *current* process's cgroup for the literal `/user@`. That substring is present only when ops already runs inside the user manager's service tree (e.g. a desktop terminal spawned by user@<uid>.service). A process started from a normal login/SSH/TTY session lives under `/user.slice/user-<uid>.slice/session-N.scope` — a sibling of user@<uid>.service, with no `/user@` component. Concrete failure: `ops run -- <agent>` over SSH → /proc/self/cgroup is `0::/user.slice/user-1000.slice/session-5.scope` → path.find("/user@") is None → returns empty Vec → enforceable_properties() empty → limiter() returns None → cgroup::wrap() returns bwrap UNWRAPPED → the cage runs with NO TasksMax/MemoryMax, so a fork-bomb or runaway allocator in the agent is unbounded — the exact anti-DoS control this module exists to provide is absent. This is NOT genuine degradation: `systemd-run --user --scope -p TasksMax=16384 -- true` from that same SSH shell succeeds (the scope is created under user@<uid>.service, which has pids/memory delegated by default), and limiter() even passes its own `$XDG_RUNTIME_DIR/bus` reachability check. doctor also prints the misleading "no reachable systemd user session or delegated controller" note. Since ops is built to run autonomous agents on servers over SSH, this disables the limit for the primary deployment. Fix: derive the user@<uid>.service cgroup path from geteuid() (or from the `user-<uid>.slice` prefix of the current path) instead of requiring `/user@` to appear in the current process's own cgroup.

**Vérif :** Traced cgroup.rs:180-205: delegated_controllers() locates the user@<uid>.service delegation root by string-searching /proc/self/cgroup for the literal "/user@". This is a genuine detection bug, not the accepted graceful-degradation residual: systemd-run --user --scope -p TasksMax=... succeeds from that same shell (scope created under user@<uid>.service, which has pids/memory delegated by default) and limiter()'s $XDG_RUNTIME_DIR/bus check passes, so ops mis-detects an available capability; the doctor note (line 320) is correspondingly misleading and the landing test (line 558) silently skips the SSH case. Severity corrected to medium because these limits are explicitly non-boundary anti-DoS hardening (module doc lines 20-24) — the impact is host resource exhaustion by the agent, not a sandbox escape or data breach.

### `src/sandbox/proxy.rs:219` — Per-host leaf cache grows unboundedly, keyed by attacker-controlled SNI, minted before any policy check
*best-practice*

**Scénario :** Ca::leaf_for caches every minted CertifiedKey in the `leaves` HashMap with no cap or eviction, and CertResolver::resolve mints for whatever SNI the ClientHello carries. The mint happens during the handshake, i.e. BEFORE the SNI==CONNECT-host check (line 881) and before the policy verdict (line 1032) — a CONNECT to any host:port is answered '200 Connection established' unconditionally on the L7 path. Failure scenario: the in-cage agent (Mode B, the adversary) loops CONNECT + a crafted ClientHello with a unique SNI per connection (no completed handshake needed, ~hundreds of bytes each); each iteration costs the host a keygen+sign and permanently adds a keypair+cert entry to the map. The proxy runs on the host OUTSIDE the cage's cgroup limits (the file itself defends this exact class at read_head_buffered, line 1618, and caps splices/ask-parks for the same reason), so host memory grows without bound (~MB/s) plus sustained keygen CPU. Fix: bound the cache (LRU/cap), or mint only for the already-known connect_host (a per-connection resolver), which also fails fronting attempts one step earlier.

**Vérif :** Traced handle_client: on the L7 path the proxy writes "200 Connection established" unconditionally (proxy.rs:870), then drives the TLS handshake via read_head_buffered (876), which invokes CertResolver::resolve (264-267) -> Ca::leaf_for (212) -> mint_leaf (keygen+sign) and insert into the leaves HashMap (218-221) — all BEFORE the SNI==connect-host check (881) and the policy verdict. The Ca is a single Arc shared across all per-connection threads (server_config in ProxyCtx, serve at 745), leaves has no cap/eviction, and entries persist past the thread, so an in-cage Mode-B agent looping CONNECT + unique valid-DNS SNIs grows host memory (outside the cage cgroup) and burns keygen CPU without bound. This is not an accepted residual; the same file explicitly caps this exact class elsewhere (ASK_PENDING_CAP:766, MAX_CONCURRENT_SPLICES, HEAD_MAX:760), making the missing leaf-cache bound an inconsistent defense gap. Medium/best-practice is honest: real host-side resource-exhaustion DoS, but bounded to the session lifetime and same-uid, not a confidentiality/escape break.

### `src/sandbox/proxy.rs:747` — A single transient accept() error permanently kills the session's egress proxy
*best-practice*

**Scénario :** serve() propagates any error from listener.incoming() with `?`, ending the accept loop; egress.rs:257 discards the result, so the proxy thread dies and never restarts — every subsequent in-cage request loses egress until the session is relaunched. accept(2) transiently fails with ECONNABORTED (peer resets before accept) and EMFILE (fd exhaustion — reachable by the agent itself: each proxy connection consumes several host fds against the default 1024 soft ulimit, so a burst of a few hundred concurrent in-cage connections triggers it). Failure scenario: agent (or a legitimately parallel fetch storm) drives fd pressure -> accept returns EMFILE -> serve returns Err -> proxy dead -> an interactive ask-posture session silently loses all egress, including for the user's own later commands. Fail-closed in direction, but standard practice is to continue on ECONNABORTED/EINTR and back off briefly on EMFILE/ENFILE rather than treating them as fatal. The egress.rs comment ('the cage then loses egress (fail-closed)') acknowledges the direction, not the transient-error-is-permanent granularity.

**Vérif :** Traced: proxy.rs:747 (`let stream = stream?;`) ends the accept loop on any accept error, and egress.rs:255-258 spawns the serve thread once and discards its result with no respawn — grep confirms no ECONNABORTED/EMFILE handling or restart logic anywhere in proxy/egress/control. The scenario is reachable: the thread-per-connection proxy consumes ~2 host fds per in-cage connection in the ops process (default 1024 soft ulimit), so a burst of concurrent in-cage connections drives accept(2) to transient EMFILE, which here permanently and silently kills all egress for the session. The egress.rs:256 comment acknowledges only the fail-closed direction, not the transient-error-is-permanent escalation, and no documented residual covers the accept loop; continue-on-ECONNABORTED / backoff-on-EMFILE is standard accept-loop practice. Severity medium (best-practice, availability-only, fail-closed direction) is honest.

### `src/sandbox/proxy.rs:749` — Uncapped thread-per-connection on the L7 path; per-read timeouts do not bound head time (slowloris drip-feed)
*best-practice*

**Scénario :** serve() spawns one host thread per accepted connection with no global cap — only raw splices (MAX_CONCURRENT_SPLICES=128) and ask-parks (ASK_PENDING_CAP=256) are bounded, both justified by 'an in-cage agent cannot pin unbounded host threads'. The same reasoning applies to plain L7 connections: the 30s timeouts set at line 750-751 are per read() call, not a per-head deadline, and read_head_raw (line 1592) reads one byte at a time — so a client dripping 1 byte per <30s holds a thread for up to HEAD_MAX(16384) x 30s (~5.7 days) per connection. Failure scenario: the agent opens N connections (bounded in-cage only by TasksMax=16384 socat forks) and drip-feeds each CONNECT head; N host threads (outside the cage's cgroup) plus their fds are pinned near-indefinitely, converging on fd exhaustion (see the accept-error finding) or host thread/memory pressure. The design record's 'socket timeouts (slowloris)' mitigation does not actually hold for a drip-feed. Fix: a global connection cap (mirroring the splice cap) and/or a wall-clock deadline for reading a head.

**Vérif :** Traced end-to-end: serve() (line 749) spawns one unbounded host thread per connection; the only host-thread caps in the module are MAX_CONCURRENT_SPLICES=128 (L4) and ASK_PENDING_CAP=256 (ask-park), and line 540's comment confirms "the inspected L7 path never touches it." The timeouts at 750-751 set SO_RCVTIMEO, which is per-recv, and read_head_raw (1592) reads one byte per read() call, so a drip-feed of 1 byte per <30s resets the clock every byte and holds a thread up to HEAD_MAX(16384)×30s ≈ 5.7 days per connection, cycled indefinitely — exactly what the module comment at 742-744 ("a slow or hung peer cannot pin a thread forever") claims is impossible. This lands squarely in the default Mode-B threat model (untrusted in-cage agent), the proxy runs outside the cage's cgroup so TasksMax/MemoryMax do not bound these host threads/fds, and it is covered by no accepted residual; the same reasoning that justified the two existing caps applies to the third path. Medium is honest: the count is finite (bounded by in-cage TasksMax and per-session proxy blast radius) but still a real host-side thread/fd-exhaustion DoS escaping the cgroup, plus a materially misleading comment.
